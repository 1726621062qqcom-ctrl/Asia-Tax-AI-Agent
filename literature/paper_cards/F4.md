# Technical Challenges in Maintaining Tax Prep Software with Large Language Models

## 1. 研究问题与作者主张

- 研究问题：作者问，能否借助预训练 LLM 协助开发者自动更新税法在软件中的实现 [p.2]；摘要把目标写成从 IRS 公告提取代码差异（code differentials），并与上一版代码自动整合 [p.1]。本文聚焦其中一环：对 LLM 生成的多个候选代码排序 [p.2]。
- 作者假设（posit）：IRS 公告中税法修订文本严谨而形式化，可自动翻译成可执行代码 [pp.1–2]；作者称现行维护依赖人工代码分析和专家解读，耗时且易错 [p.1]。
- 作者讨论的难点：oracle problem [p.2]，以及因隐私和法律顾虑难以获得带标签的个人报税数据 [p.4]；LLM 输出的多个候选特征可能差异很大，排序是 key challenge [p.2]；带逻辑错误的代码未必能从结构上看出 [p.6]。
- 作者报告：CodeBertScore 等现有指标常不能让误差最小的候选排在最前；引入 MajorityVote 后，两者组合的结果超过任一单独指标 [pp.2–3]。验证与精化（metamorphic testing、Feedback Prompt Generator）属于作者所说的后续阶段 [p.3] [pp.8–9]。

## 2. 方法

框架（Figure 4）为循环流程 [p.7]：
1. 输入：上一年税务软件代码与当年 IRS 公告中的税法更新；另做不含上一年代码的实验 [p.7]。无上一年代码时，Figure 2 图注写明图中列出的上一年代码只用于说明 CodeBertScore 的计算，不影响代码生成 [p.5]。
2. 生成：LLM 在一系列 prompt 引导下生成多个候选；比较 ChatGPT3.5 与 GPT4.0 [p.7]。
3. 排序 [pp.7–8]：CodeBertScore 用 CodeBERT 计算生成代码与上一年参考代码、IRS 政策更新之间的 cosine similarity。MajorityVoteScore 用一组随机输入（覆盖多种收入水平、filing status 等）运行全部候选，取每个输入上最常见的输出并假设其正确，得分为候选输出与之一致的输入所占百分比。WeightedScore 为两者的加权平均；作者称经多次实验取 CodeBertScore 0.6、MajorityVoteScore 0.4 [p.8]。
4. 验证与反馈 [p.8]：对排名最高的候选做 metamorphic testing，通过则视为正确，失败则由 Feedback Prompt Generator (FPG) 分析失败并生成针对性 prompt，可迭代多次。本文只讨论排序 [pp.8–9]。

实验设计：对 2021 税年生成 tax brackets、tax deductions、EITC 三类计算的函数 [p.2]（场景名 Brackets、Brackets + Deductions、Brackets+Ded+EITC [p.10]）；2 个 LLM（GPT-4.0、GPT-3.5）× 2 种条件（附 2020 年参考实现；不附，即 direct prompting）[p.2]；每种设置生成 10 个候选 [p.2]。Prompt 含 Objective、Data Structures、User Inputs、Requirements 和税政数据，附代码条件另加 Reference Python Code [p.10] [p.13]。评价为与 ground truth 实现比较，并在容忍阈值 δ 下统计准确率 [pp.2–3]。

先前工作（参考文献 17、18）：5 个领域的 33 条 metamorphic specifications，用一阶逻辑表达，例如 blind 纳税人应获得不低于非 blind 纳税人的税收待遇 [p.4]；TenForty 据此生成数以万计的随机测试，并用 CART 决策树解释违反情形 [pp.4–5]。

## 3. 数据与范围

- 法域与税种：美国联邦个人所得税；LLM 实验针对 2021 税年，参考代码为 2020 年 [p.2] [p.12]。
- 提示中的输入：Brackets 提示含 income 与 marital_status（1–4，对应 4 种 filing status）[p.9]；Brackets+Deductions 提示另含 age 与 blindness status [p.12]；EITC 场景的提示原文未展示。
- 模型：OpenAI 的 GPT-4.0 与 GPT-3.5 [p.2]；摘要还提到 Llama [p.1]，正文只报告前两者。
- 样本：每种设置 10 个候选，表中列排名前 4 [p.10] [p.14]。
- 语言：提示要求 Python 脚本 [p.9] [p.12]；Discussion 称初始研究（Fall'23 和 Spring'24）主要针对 C 语言代码 [p.16]；Tables 1–2 所用语言原文未说明。
- 先前工作的数据：OpenTaxSolver，2018、2019、2020、2021 税年 [p.4]。
- 原文未说明：实验所用的具体 IRS 公告、模型版本与采样参数、随机输入的数量与生成方式、Ground Truth Score 分母 100 的含义、ground truth 实现的来源、是否重复生成。

- 例示 [pp.5–6]：Figure 2（无上一年代码）中，TAX_BRACKETS 字典定义不完整的 'Faulty Generation' 的 CodeBertScore 为 0.852，'Correct Generation' 为 0.871，其 ground truth score 为 0.45；Figure 3（附上一年代码）中，含逻辑错误（税档与税率可能错位；盲人扣除额可能重复计算）的 'Faulty Generation' 为 0.972，'Correct Generation' 为 0.977。
- 先前工作的结果 [p.3] [p.5]：作者称已演示一个开源税务软件项目未能正确更新代码以反映新税法 [p.3]；TenForty 在 OpenTaxSolver 上发现三类故障：缺少部分资格条件（如 married filing separately 不能申请 earned income credit）；计算所得退税接近 0（小的非零值）时不满足正确性要求；更新版（如由 2020 版更新的 2021 版）中允许用户显式选择某选项的功能在边界情形下不满足部分正确性要求 [p.5]。

### 4.2 作者的解释或推论

- 无上一年代码 [p.11]：作者写道各场景总体表现较低，两个模型的 MV 与 CBS 均低于有参考代码时，原因是 LLM 须自行构造逻辑；GPT-4 始终优于 GPT-3.5，作者认为这表明它理解指令并从零生成正确代码的能力更高；加入 deductions 和 EITC 后两个模型的准确率下降，GPT-3.5 尤甚。
- 高 MV 与低 GT 并存 [p.11]：作者认为这说明 LLM 有时生成稳定产出最常见输出、但仍含细微错误的代码，需要考虑其他排序指标及其组合。
- Figure 5 [pp.11–12]：作者写道 GPT-4.0 生成代码的输出几乎总在 ground truth 的 10% 误差内，认为这表明逻辑大体成立、只有一些小问题；GPT-3.5 不能稳定地从零生成高质量代码，在没有至少 2 份输出一致的好代码时尤其脆弱。
- 附上一年代码 [p.13] [p.14] [p.15]：作者写道对比 Table 2 与 Table 1，提供上一年代码使表现提高（原文用词 significantly）；两个模型在各场景表现均为 good，GPT-4 的 CBS 和准确率一直高于 GPT-3.5 [p.14]。作者称 GPT-3.5 在最复杂场景的排名靠前候选好于 GPT-4（GT 为 56、56、35、35 对 48 ×4），结果出乎意料，但 GPT-3.5 缺乏一致性、也生成了错误逻辑的代码，GPT-4.0 的代码逻辑更正确、更稳定 [pp.14–15]。作者认为随场景变复杂 GT 下降而 MV 仍高，说明存在不影响最常见输出的细微错误；EITC 逻辑即使有上一年代码仍难以准确实现，可能需要更复杂的 prompt 策略或额外知识来源 [p.15]。
- 容忍阈值 [p.15]：作者认为在较大容忍度下，GPT-3.5 在上一年代码引导下可能适合允许较高误差的场景，精度优先时 GPT-4.0 仍是首选。
- 排序方法 [pp.6–7] [pp.15–16]：作者写道仅靠语义相似度不能保证代码正确，MajorityVoteScore 用于发现结构或语法上看不出的逻辑错误；作者认为结果进一步支持其排序方法，称其能找出有潜力精化为完全正确实现的候选，尤其是 GPT-4.0 的候选。
- Discussion [p.16]：作者写道较小的 LLM 现已能准确修改已有 Python 代码以纳入新数值并适应税政更新，并称这一进展与代码排序无关；新框架正通过 symbolic execution 在更多 LLM 和更复杂场景中测试，初步结果显示较小的 LLM 也能达到较高准确率；该处未给出数字。

## 5. 作者陈述的局限与前提

- 前提：MajorityVoteScore 把最常见输出假设为正确答案 [p.8]；成功条件被定义为通过全部 metamorphic tests 并取得某种统计性或形式化的正确性保证 [p.8]。
- 权重设置依赖 LLM 能力：对能力较强的 LLM（如 GPT-4）多数票分数是可靠的指标，对能力较弱的 LLM（如 GPT-3.5）过度依赖多数票可能导致误判 [p.8]。
- 高 MV 与低 GT 并存说明一致输出的代码仍可含细微错误 [p.11]；GPT-3.5 在没有至少 2 份输出一致的好代码时尤其脆弱 [p.12]。
- 作者写道即使在 7% 误差范围内达到 100% 准确率，仍表明存在需要精化的错误 [p.12]。
- 本文只处理排序；把 metamorphic testing 集成为验证组件还需更多工作，Feedback Prompt Generator 可能并不简单，需要大量后续工作 [p.9]；验证阶段是计划中的下一阶段 [p.3]。
- Discussion 中新框架与较小 LLM 的结果称为 preliminary [p.16]。
- 文中没有专门的局限性小节。

## 6. 关键术语

- Oracle problem：作者称税务软件的正确性要求没有显式给出，因为正确的报税结果对个人纳税人高度主观 [p.2]；确定个人决策的正确输出耗时、昂贵且易错 [p.4]。
- Metamorphic relation / specification：用一阶逻辑表达的合规性质，把一个纳税人与一个反事实的纳税人联系起来；正确性也要与处境相似的纳税人比较 [p.2] [p.4]。
- CodeBertScore：用 CodeBERT 计算生成代码与上一年参考代码及 IRS 政策更新之间的 cosine similarity [pp.7–8]。
- MajorityVoteScore：候选的输出与全部候选在同一输入上最常见输出一致的输入所占百分比 [p.8]。
- WeightedScore：CodeBertScore 与 MajorityVoteScore 的加权平均，文中权重为 0.6 与 0.4 [p.8]。
- Ground Truth Score：表中以 x/100 给出 [p.10]；p.6 称其也叫 validation score [p.6]；p.11 称 Table 1 呈现的是生成候选的 absolute accuracy [p.11]。
- δ：容忍阈值，作者的表述为 a solution within δ% of ground truth is considered correct [p.3]。
- Feedback Prompt Generator (FPG)：分析 metamorphic testing 中的具体失败并生成针对性 prompt，引导 LLM 下一轮生成更准确的代码 [p.3] [p.8]。

## 7. 原文摘录

- "We posit that the rigor and formality of tax amendment language, as expressed in IRS publications, makes it amenable to automatic translation to executable specifications (code)." [p.1]
- "Can we leverage recent breakthroughs in AI, in particular with pre-trained LLMs to assist software developers in automatically updating the implementation of tax law in software artifacts?" [p.2]
- "Interestingly and somehow surprisingly, when prompted with the code context, GPT3.5’s candidates achieved a similar or better accuracy, compared to GPT4.0’s candidates, when δ sets to at least 4%." [p.3]
- "... more work is needed to integrate it as the validation component in the framework 1." [p.9]
- "A crucial observation is the occasional disparity between high majority vote accuracy and significantly lower ground truth matching scores." [p.11]
- "However, it’s important to note that achieving perfect accuracy at a 7% error margin still indicates the presence of errors that require refinement." [p.12]
