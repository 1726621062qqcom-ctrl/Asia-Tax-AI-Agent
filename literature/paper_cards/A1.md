# Catala: a programming language for the law

## 1. 研究问题与作者主张

- 问题与目标：作者讨论 computational law（又称 rules as code），即法律中实体定义明确、且一般不期望需要 human appreciation、judgement 或 interpretation 的那一部分，例如 tax law、family benefits、pension computations 等，并称这些都是 'algorithms in disguise' [p.2]。作者认为，散文式法条会留下歧义，分散在多页的条文使预期结果难以算出，自然语言还会遗漏 corner cases [p.1]；目标是设计一门能把 statutory law 直接而系统地翻译成可执行实现的编程语言 [p.1]。作者引述的动机案例有：法国军队薪资系统（涉及 174 种奖金与补贴）三次重写尝试后被废弃 [p.2]；因 IRS 的错误实现，近一百万美国人收到错误的 Economic Impact Payment 或没有收到 [p.2]。
- 设计主张：作者称 Catala 遵循现有法条的结构，使一段法条与其 Catala 译文之间一一对应 [p.3]；其底层使用 prioritized default logic，作者称据其所知，Catala 是首个以该逻辑为核心系统设计的编程语言 [p.3]；作者称 Catala 有 clear semantics，编译到通用 lambda calculus，再可译为任何现有语言 [p.3]。
- 正确性与评估主张：作者称已实现编译器，并用 F★ 证明助手证明其核心编译步骤正确 [p.1]；作者称评估（含用户研究）表明 Catala 可以 'successfully express' 美国 Internal Revenue Code 与法国家庭福利计算中的复杂部分 [p.3]；摘要称评估中发现了法国家庭福利官方实现中的一个 bug [p.1]。
- 对协作、信任与适用性的主张：作者称，形式化过程中观察到 Catala 使律师与程序员有 'rich interactions'，增进对 original legislative intent 的理解，并产出可被更大软件生态复用的 'correct-by-construction executable specification'，因而 'increases trust in legal institutions' [p.1]。作者称 Catala 的设计过程与 code co-production 流程 'maximizes the potential for adoption by professionals'，并以早期用户研究和一个端到端用例支持该说法 [p.23]。作者认为 general case / exceptions 控制流等特征 'seem to be universal features found in all statutes'，并据与 S. Lawsky 的交谈等 'posit' Catala 'captures the fundamentals of legal reasoning' [p.11]。
- 与既有工作的关系：作者将 Catala 与 Allen (1956)（主张用符号逻辑消除法律歧义，但未提供可操作的翻译工具）和 Sergot et al. (1986)（用 Prolog 形式化 British Nationality Act；作者称该文承认在表达否定上有 'a major limitation'，且未采用 literate programming）作比较；作者称自己关注维护大型组织中现有的 legal expert systems，目标是 'an industrial-grade tool' [pp.26–27]。

## 2. 方法

- 法条结构分析 [pp.3–6]：作者以 US Internal Revenue Code Section 121（'Exclusion of gain from sale of principal residence'）为贯穿全文的示例，理由是它以英文写成、包含作者想处理的全部难点、且被充分研究 [p.3]。作者逐段指出：(a) 给出一般规则（出售前 5 年内作为 principal residence 拥有并使用合计 2 年以上），上限 $250,000 要到 (b)(1) 才出现 [p.4]；(b)(2)(A) 在特定条件下以 $500,000 替换 $250,000，作者称这是 backpatch [p.4]；(b)(2)(B) 要求把配偶视为未婚分别计算再求和，作者称法条因此 re-entrant [p.5]；(b)(3) 在特定条件下取消 (a)，(b)(4) 在较早日期的情境下再次调用 (b)(2)(A)，作者称这相当于一个绑定出售日期的 hidden lambda [p.5]。
- 逻辑基础 [p.6][p.12]：default logic 的 default 形如 a : b_i / c（若 a 成立且各 b_i 与已知事实一致，则 c 成立）；prioritized default logic 在 default 之上加严格偏序，以解决冲突 [p.6]。作者称 Lawsky (2018b) 主张这一版本最适合表达法律，作者赞同并采用 [p.6]。Catala 使用其受限形式：每个定义自成一个 'world'，带静态 pre-order，优先级编码在语法树中 [p.12]。
- 表层语言 [pp.6–11]：
  - metadata 先枚举与问题相关的结构、实体与变量，再给出变量间的定义与关系；内置类型有 date、duration（以天数表示）、condition（布尔）、money、collection；scope 在直觉上是函数，context 变量是其参数与局部变量 [p.7]。
  - rule 用于 condition（法律中默认 false），definition 用于其他类型（无默认值）[p.8]；exception 使某个定义优先于另一个，允许任意的 exceptions 树；运行时同一变量有多于一个适用定义且无优先关系，则以致命错误中止 [p.10]。优先级在语法中静态给出 [pp.8–9]；读取未指定的 context 变量也中止 [p.8]。
  - 作者称 Catala 不提供内置的年时长，须由用户指定法条中 'two years' 的含义；示例中 'periods aggregating 2 years or more' 被写成 >=^ 730 day [pp.7–8]。
  - 定义可乱序书写，解释器做 topological sort，环路被拒绝 [p.9]；每段法条原文之后紧跟其 Catala 转写（literate programming）[p.9]。作者称表层语法与律师合作设计，律师 'confirmed that the generous keywords improve readability' [p.7]。
- 编译链 [pp.11–18][p.21]：表层语言，经 desugared language、scope language、default calculus，到带 list、option 与 exception 的 lambda calculus，再到 OCaml（经 js_of_ocaml 可到 JavaScript）或 interpreter [p.11][p.21]。
  - default term 写作 ⟨e_i | e' :- e''⟩：依次求值各 exception；两个或以上有效（不是 ∅）则抛出 conflict error ⊛；恰有一个有效则结果为它；无有效 exception 时，e' 为 true 则结果为 e''，为 false 则结果为 ∅ [pp.11–12]。⊛ 在任何 context 下都中止归约，∅ 只传播到外层 regular context [pp.14–15]。
  - 脱糖把分散的定义与 exceptions 整理为每个变量一棵 n 叉树，并做两次 topological sort，检测到环路即报错 [pp.12–14]；scope 与 call 被替换为 lambda 抽象与应用，context 变量被 thunk [pp.14–16]。
  - 到 lambda calculus 时，辅助函数 process_exceptions 对 exception 列表做 fold_left，以 None/Some 累加器计数非空 exception，累加器已为 Some 时再遇到非空 exception 则抛出不可捕获的 ⊛；无非空 exception 时退回 if e_just then e_cons else raise ∅ [pp.16–18]。
- 形式验证 [pp.19–20]：作者在 F★ 中机械化了 default calculus、目标 lambda calculus 的语义和翻译方案，证明类型保持和模拟两条性质 [p.19]。因翻译引入 thunk，常规的单步模拟图（Fig. 11 A）不适用，实际成立的是 Fig. 11 B：翻译后的两个项 le 与 le' 最终归约到同一个 target [p.19]。目标演算内置 list、fold 与 option，不支持用户定义的代数数据类型 [p.20]。
- 编译器与后端 [pp.20–23]：编译器以 OCaml 实现，采用多级中间表示 [p.20]；解释器带 log hooks，可显示每个被采用的定义在法条中的位置 [p.22]。后端采用直接源代码生成而非 API 或 FFI；作者称这一方案 'generally impractical'，但 Catala 的有意简化使之可行 [p.22]。
- 评估设计：性能计时 [p.22]；访谈 [p.23]；18 名法学研究生的两轮问卷 [pp.23–25]；两个法律文本的形式化及对比 [pp.25–26]。

## 3. 数据与范围

- 法律文本：(1) 美国 Internal Revenue Code Section 121，形式化到 (b)(4)，约占整节的 15%，约 350 行（含法条文本）；作者称它是 'complexity benchmark for legal statutes'，一位律师合作者认为它是 'one of the most difficult sections of the tax code' [p.25]；(2) 法国家庭福利的整个计算，约 1,500 行（含法条文本），涉及 French Social Security Code 的 27 条与多项 executive orders [p.26]；该福利按家庭受抚养子女数发放，设立于 1930 年代初 [pp.25–26]。作者称评估对象为 'several legal texts' [p.1]；对 Catala repository 中的其他示例，文中只称源代码结构与法条结构一致 [p.18]，未逐一描述。
- 法域与语言：美国联邦税法（Section 121 以英文写成 [p.3]）与法国社会保障法（Catala 代码以法语写成 [p.25]）。作者称在其他美国法律和非美国法律体系中也见到相同的写法模式 [p.6]；被检视的其他法条清单，原文未说明。
- 用户研究样本：N = 18 名法学研究生，就读于 Université Panthéon-Sorbonne 的硕士项目 'Droit de la création et numérique'（Intellectual Property and Digital Law）；匿名招募；会前口头询问，均无编程经验 [pp.23–24]。
- 访谈：作者对 'a high-profile French administration' 内的法律专家系统程序员与律师做了 'Exclusive interviews'；受访人数、时间与提纲，原文未说明 [p.23]。
- 对照对象：官方模拟器 mes-droits-sociaux.gouv.fr，以及 OpenFisca 项目中家庭福利的 365 行 Python 源文件；作者称官方模拟器的源代码包含在 OpenFisca 中 [p.26]。
- 性能基准：法国家庭福利程序（约 1500 行 Catala 代码），输入为一户法国家庭的描述，输出每月家庭福利金额；作者称其复杂度与 Section 121 相当 [p.22]。测试机器、运行次数与输入个数，原文未说明。
- 补充材料：作者所引 artifact（Zenodo DOI 10.5281/zenodo.4775161 [p.28]）含 Section 121 的建模、用户研究的完整回答与法国家庭福利代码 [p.24][p.25]；本卡片未读取。

## 4. 结果

**实证结果（作者报告的数字与观察）**

- Section 121 的形式化规模：已形式化到 (b)(4)，约占整节的 15%，约 350 行（含法条文本），作者称这部分包含其核心与最常用的 exceptions；由作者与专攻 US Internal Revenue Code 的律师通过四次各 2 小时的 pair programming 完成；其余部分 'left as future work' [p.25]。
- 法国家庭福利的形式化规模：约 1,500 行（含法条文本），6 个 scope，63 个 context 变量，83 个 definitions 与 rules；代码以 OCaml 库形式发布，并驱动一个在线模拟器 [p.26]。
- 与官方模拟器比较：写好代码和一些测试用例后，与官方模拟器 mes-droits-sociaux.gouv.fr 比较结果，'found no issue'；官方模拟器没有儿童由社会服务机构监护的情形，该情形无法比较 [p.26]。
- 与 OpenFisca 比较：检视 OpenFisca 中 365 行 Python 的家庭福利源文件后，发现与 Catala 实现有一处差异：依 Social Security Code 第 L755-12 条，海外领地的独生子女家庭不适用家庭福利收入上限；OpenFisca 未考虑这一点，作者披露后已修复 [p.26]。摘要把这一发现表述为 'a bug in the official implementation of the French benefits' [p.1]。
- 性能：法国家庭福利程序（约 1500 行 Catala 代码）在 Catala 解释器中约 150ms，编译到 OCaml 后 0.5ms [p.22]。
- 规模与工作量：编译器约 13,000 行 OCaml [p.20]，作者估计开发工作量为 5 person-months [p.21]；F★ 机械化约 3,500 行，耗时 1 person-month，全部验证时间 'of the order of a few minutes' [p.20]；OCaml 后端为 350 行编译器代码加 150 行运行时代码（不含 zarith 与 calendar 库）[p.23]。
- 证明与设计中的修正：作者称在机械化过程中才发现常规模拟定理（Fig. 11 A [p.19]）不成立，需改证变体 B，并对证明仍需 3,500 行 F★ 'surprised' [p.20]；最初带运行时 pre-order 的一般 prioritized default logic 表述使语义 'nearly impossible to explain'、证明 'very challenging'，因此去掉运行时 pre-order [p.18]。
- 访谈观察：作者称法国行政机构 'always' 采用 V-shaped development cycle：律师写自然语言规格说明，IT 部门程序员据此编码，常不再回看法条原文 [p.23]；访谈显示该分工 'artificial'：规格说明对程序员常 'insufficient or ambiguous'，需花数小时与律师通话澄清，实现的验证依赖律师编写的测试用例，其数量与质量受预算限制 [p.23]。
- 用户研究题目（Table 2）：(1) 是否理解 Catala 项目；(2) 能否读代码而不头痛（'getting a headache'）；(3) 能否理解代码；(4) 能否把代码与其编码的法律含义联系起来；(5) 能否 'certify' 代码恰好做了法律规定的事、不多不少，若不能是否有错 [p.24]。
- 用户研究回答统计（N = 18；作者把自由文本回答归为 positive / mixed / negative；数值取自 Fig. 15 与 Fig. 16 柱上标注，单位为人数）[p.24]：

| 题号 | 第一轮 positive / mixed / negative | 第二轮 positive / mixed / negative |
|---|---|---|
| (1) | 18 / 0 / 0 | 14 / 0 / 0 |
| (2) | 8 / 6 / 5 | 12 / 2 / 1 |

- 故意植入的 bug：展示给参与者的代码中故意植入了一个 bug（一个 ⩽ 运算符被换成 ⩾）；第二轮 Q(5) 回答 'Yes' 的 7 人中，2 人发现了它 [p.25]。
- 一名参与者事后联系作者，希望加入 Catala 项目并建模法国继承法 [p.25]。

**作者的解释或推论**

- 作者称早期结果 'while lacking the rigor of a scientific user study' 表明律师对 literate programming 范式的接受 'relatively good'；两轮之间 positive 回答出现 'significant increase'，表明律师起初感到困惑，但在 15 分钟 Q&A 之后能快速抓住 Catala 的意图与要点 [p.25]。
- 作者称第二轮 Q(5) 的大量 negative 回答可能源于法国律师不熟悉美国 Internal Revenue Code；'certify' 一词暗含律师有把握在法庭上为其意见辩护；作者相信，对已形式化法条的熟悉加上基础 Catala 培训可使律师的信心达到该水平 [p.25]。
- 作者把 7 人中 2 人检出植入 bug 解读为 'a very encouraging indication that lawyers can make sense of the Catala code with just a two-hour crash course' [p.25]。
- 作者称访谈所得的 insight 'suggests' 从一开始就让律师与程序员共同参与的更敏捷流程 'would be more efficient'，并称 Catala 是 'the right tool for the job' [p.23]。
- 作者称对 Section 121 的早期估计表明，形式化整部 US Internal Revenue Code 对一支小型跨学科团队而言，在给予几年时间的条件下是 'a completely reachable target' [p.25]；作者称 'we are confident' Section 121 其余部分可用 Catala 表达，理由是 'the maze of exceptions is localized to (a) and (b)' [p.25]；同时称进展 'relatively slow'，因为要考虑每种可能出现的情形 [p.25]。
- 作者称解释器性能 'acceptable even for a production environment'，并作结论 'performance problems are, at this stage of the project, nonexistent' [p.22]；称 F★ 机械化 'significantly increases our confidence in the Catala compilation toolchain' [p.20]。
- 作者称一句 Section 121(a) 的形式化就需显式声明隐含概念（如一年的定义）并澄清歧义（如时间段是否可重叠）[p.9]；称形式化法律与用证明助手形式化软件 'no different'，两者都能在已有软件中发现 bug 并加以报告和修复 [p.26]。
- 作者认为上述法国家庭福利的规模数字 'fairly representative' 于一份 'medium-size legal document' 所需的撰写工作量 [p.26]。
- 作者称（原文用 'we claim'）可编译到任何具备 functions、arrays、structures、unions 与 exception 支持的编程语言 [p.22]；文中演示的是 OCaml 后端，并经 js_of_ocaml 到 Web [p.23]。

## 5. 作者陈述的局限与前提

- 适用范围：作者称通用的分类系统在需要大量 human judgement 的情形下 'remains an elusive prospect'，因此关注 computational law [p.2]；作者称 'the authors do not anticipate a drastic improvement around the world concerning legal complexity'，因而称改进只能寄希望于编程语言与工具 [p.2]。
- 对法律的前提：作者称法条没有一般递归和循环依赖（'the law does not have general recursion' [p.11]；'the law is not supposed to have dependency cycles' [p.9]），并称在其工作中 'never encountered a circular reference' [p.5]。
- 语言设计上的限制：语言 'purposefully' 不是 Turing-complete [p.11]；不允许引用 sub-scope 的 sub-scope，也未实现在任意深度覆盖定义，因为作者尚未找到需要它的法条 [p.11][p.18]；第 4 节的形式化省略了 data types 等辅助特性 [p.11]；同一变量有多个适用定义且无优先关系时执行中止，作者称这表明 'either programmer error, or a fatal flaw in the law' [p.10]。
- 作者说明的后续改进：context 变量的输入/输出标注 [p.7]；不依赖 exception 的编译方案 [p.22]；把日志扩展为面向法律的结果解释，作者认为这 'can easily' 实现 [p.22]；完成 Section 121 的形式化 [p.25]。
- 形式证明的范围：证明不涵盖全部语言特性；目标演算不支持用户定义的代数数据类型，作者认为这不构成局限（'We believe this is not a limitation'）[p.20]；F★ 提取的代码未用于编译器，理由为证明未涵盖全部特性、翻译在编译器和证明中各约 100 行可并排比较、编译器的位置与错误信息工程难以传入证明 [p.20]。
- 使用者预期：作者称 'we don't expect lawyers to use Catala unaccompanied' [p.21]，也称 'We do not expect lawyers to write Catala code by themselves'，设想律师担任观察者与审阅者 [p.23]；作者称建模法律 'labor-intensive'，其经验是最好由 Catala 专家与法律专家 pair-programming 完成 [p.10]。
- 用户研究与比较：作者称其早期结果 'lacking the rigor of a scientific user study' [p.25]；官方模拟器缺少社会服务机构监护的情形，该情形无法比较 [p.26]。

## 6. 关键术语

- **computational law / rules as code**：作者称法律中的一个子集，涉及实体定义明确、一般不期望人的 appreciation、judgement 或 interpretation 的情形；这类法律 '(roughly) defines a function that produces outcomes based on a set of inputs' [p.2]。
- **prioritized default logic**：default logic 的一种改进，default 值由 justification 守护，default 之间可按相对优先级排序；形式上加一个严格偏序以解决冲突 [p.6]。
- **default term ⟨e_i | e' :- e''⟩**：Catala 内部表示变量取值的形式，e_i 是 exceptions，e' 是前提，e'' 是结论，对应 default logic 中的 a : b_i / c [p.11]；求值规则见 [pp.11–12]。
- **scope / context variable**：scope 体现法条隐含的模块性，直觉上是函数；context 变量是其参数与局部变量，其值可能稍后由上下文确定 [p.7]。
- **rule / definition / exception**：rule 用于 condition，是以 false 为基本情形的布尔定义；definition 用于其他类型；exception 声明某个定义的优先级高于另一个定义 [p.8][p.10][pp.12–13]。
- **conflict error ⊛ / empty error ∅**：⊛ 在两个或以上 exception 同时有效时产生，使归约中止；∅ 表示 default 不适用，可被外层 default 的 exception 列表捕获 [p.12][pp.14–15]。
- **literate programming**：每段法条原文之后紧跟其 Catala 转写，作者引用 Knuth (1984) [p.9]。
