# QuickCheck: a lightweight tool for random testing of Haskell programs

## 1. 研究问题与作者主张

- 目标：作者介绍 QuickCheck，一个帮助 Haskell 程序员 formulate 并 test 程序 properties 的工具；properties 写成 Haskell functions，可在随机输入上自动测试，也可自定义 test data generators；作者给出若干 case studies，称工具在其中 was successfully used，并指出一些 pitfalls [p.1]。
- 动机：作者写道 testing 占软件开发成本 up to 50%；有 anecdotal evidence 表明函数式程序需要的测试 somewhat less，但测试仍是函数式开发的 major part [p.1]。
- 设计主张：以 formal specifications 为可自动检查的判据（借助 class system 嵌入 Haskell 的 domain-specific language）；用 random testing 生成用例，作者称它在实践中 competes surprisingly favourably with systematic methods；test data 的分布由测试者经嵌入 Haskell 的 generator 语言控制；实现 lightweight，为单个 Haskell'98 module，about 300 lines [p.1]。
- 适用性主张：作者认为 random testing 特别适合函数式程序，因为 properties 可在 fine grain 上陈述；函数由分别测试过的组件构成时，random testing 足以对被测定义取得 good coverage [p.1]。作者写道很难说清测试方法检出故障的有效性，但 QuickCheck 在从 small experiments 到 real systems 的多种应用中 works well in practice [pp.1–2]；结论称这些 old techniques 的组合对 Haskell works extremely well [p.11]。

## 2. 方法

- Property 与 quickCheck：property 是返回 Bool 的 Haskell function，如 `prop_RevApp xs ys = reverse (xs++ys) == reverse ys++reverse xs`；quickCheck 把它作用于大量随机参数（示例为 100 个），全为 True 则报告 OK，否则报告 counterexample；测试数可作为参数指定；多态 property 须用 type signature 固定到 monomorphic 类型；作者约定除特别说明外只量化 completely defined finite values [p.2]。
- 函数与条件：量化函数的 property 借助 extensional equality `===` [p.2]；条件 law 用 implication combinator `==>`，结果类型为 Property，不满足条件的候选被丢弃并重新生成，直到凑够 100 个满足条件的用例，候选数有上限（default 1000），超限则报告实际通过数 [pp.2–3]。`classify`、`collect`（打印 histogram）监控用例分布，`forAll` 指定 generator [p.3]。
- Generator：class `Arbitrary` 含 `arbitrary :: Gen a` [p.3]；`Gen` 由 `Rand -> a` 改为 `Int -> Rand -> a`，Int 是 size bound；Gen 是 Monad，bind 通过 split 随机种子得到独立种子；组合子有 `choose`、`oneof`、`frequency`、`sized` [p.4]；size bound 是全局参数，不在子部件间分配，每个 property 的测试从小 size 开始逐步增大 [p.5]。user-defined types 的 generator 由用户编写，作者说不用 pre-processor 或 polytypic programming 自动生成 [p.4]。
- 随机函数：`Coarbitrary` 的 `coarbitrary`、`variant` 与 `promote` 把参数转为 generator transformer，由此得到 `a->b` 的 Arbitrary 实例 [p.5]。
- 实现：`Property = Prop (Gen Result)`，Result 记录布尔结果、test data 分类和参数；class `Testable` 的实例有 Bool、`a->b`、Property [p.6]；附录给出除 `quickCheck` 外的库实现 [p.12]。评估以 Section 5 的叙述性 case studies 给出，原文未报告对照实验或覆盖率数据 [pp.6–9]。

## 3. 数据与范围

- 本文不使用数据集或基准；原文未给出被测程序的数量，也未给出检出故障的汇总统计。
- Case studies（Section 5）：作者开发的 unification 算法及其 QuickCheck specification，原文称太大而不详述 [p.6]；Lava（嵌入 Haskell 的硬件描述、模拟与验证工具）及作者开发的一组 arithmetic circuits [pp.7–8]；作者为教学实现的两种命题逻辑子句集矛盾检查方法，Davis-Putnam 与 Stålmarck [p.8]；Andy Gill 转述给作者的 pretty printing 库开发经历 [p.8]；Chris Okasaki 的 Edison（高效数据结构库）[pp.8–9]。
- 工具范围：Haskell 程序；实现为单个模块，主要在 Hugs 中使用，另有调用脚本，不依赖特定 Haskell 系统；只能测试在 Haskell 内可表达且可观察的 properties [p.1]。

## 4. 结果

**工具输出示例（作者演示，不是实验）**

- 对 `prop_RevApp` 调用 quickCheck 输出 `OK: passed 100 tests.`；量化函数的 law 找到 counterexample 时只显示 `<<function>>`，作者说此时知道 law 为假但不知原因 [p.2]。
- `classify` 示例输出 `OK, passed 100 tests (43% trivial).`；`collect (length xs)` 的 histogram 中长度 0 占 49%，作者据此说只有 19 个 cases 检验了长度大于一的 list，并解释为 precondition `ordered xs` 使分布偏向短 list（长度 2 的 list 只有 50% 是 ordered）；改用 `orderedList` generator 后输出 `OK: passed 100 tests` [p.3]。

**Case studies 中作者报告的结果**

- Unification：unifier 本身 no errors at all were found；QuickCheck 发现 specification 的错误，`subst s (subst s t) == subst s t` 仅对 acyclic substitutions 成立，由 `verboseCheck` 发现，随后加上 `acyclic s` 前置条件；specification 错误的总数：原文未说明 [p.6]。作者写道 formulating the specification correctly 花了 quite a lot of work，perhaps more than writing the implementation [p.7]。
- Unification：前置条件为 `s /= Nothing` 的 properties 全部通过，但满足前置条件的用例中 over 95% 属于其中一个 term 是 variable 的情形，作者写道 they can hardly consider that the properties were thoroughly tested；改用 `probablyUnifiablePair` generator 后，trivial cases 的比例降至 20–25% [p.7]。作者另将 `Var`、`Name` 定义为 newtype，以便为 `Name` 使用专门的 generator [p.6]。
- Lava：作者写道加入 QuickCheck turned out to be quite straightforward [p.7]；理由有二：外部 theorem prover 很 heavyweight（验证 32-bit multiplier 时公式 quite big），且 provers 至多处理 first-order logic，随机生成函数则使 combinators 的 properties 可对任意 circuits 测试，代价是须固定 circuits 的类型 [pp.7–8]。作者开发 arithmetic circuits 时此前的测试 very limited and ad-hoc；发现 formal verification 同样能发现的 logical errors，以及与随机输入 size 有关的错误（formal verification 只针对 specific input sizes，常发现 had forgotten to define one of these cases）；错误数量：原文未说明 [p.8]。
- Theorem proving：用 property 对照 Stålmarck 与 Davis-Putnam 两种实现，QuickCheck found 3 bugs，作者称源于 implicit unjustified assumptions：两种实现都假设输入子句不含同一 literal 两次，Stålmarck 函数还假设没有空 clause；测试该 property 用时 about 30 seconds，Nothing 与 Just m 的分布 about 50/50 [p.8]。
- Pretty printing（Gill 的报告）：Gill 写到用 properties 对照 functional 与 imperative 两种实现，发现 three problems，第三个显示他合并了两个不应合并的概念；他为 `Arbitrary` 增加 `smaller :: a -> [a]` 以缩小 counterexample，作者报告 in some cases much smaller counterexamples were found [p.8]。
- Edison（Okasaki 的报告）：Okasaki 报告自己 mostly a very satisfied user，测试 Edison 的 effort 为先前 test suite 的 probably 25%（括注 maybe less!），并称 does a much better job [pp.8–9]；他也提出一个 drawback：specification module 须 import 被测 implementation，每次测试前要手工编辑该 module [p.9]；错误数量：原文未说明。

**作者引述的他人结果与自身经验（Section 6）**

- Duran 与 Ntafos（1984）比较 random testing 与 partition testing，发现 differences in effectiveness were small，Hamlet 与 Taylor 重复并 corroborated；作者写道 partition testing slightly more effective at exposing faults，并转述 Hamlet 的综述：在 random test 中多取 20% 的点，partition test 可能有的优势即被抹去 [p.9]。
- 作者报告其经验：Maurer 提高生成叶子概率以保证终止的做法使 trivial test cases 的比例 far too high [p.10]。
- 作者观察到发现的错误大致平均分布在 test data generators、specification、program 三类；作者称第一类 useless to discover（有助于进一步测试的情形除外），第二类即使未揭示代码错误也揭示对代码的 misunderstanding [p.11]。

**作者的解释或推论**

- unifier 中未发现错误：作者认为这 probably 更多反映作者此前多次编写 unifier 的经验，而非 QuickCheck 的 effectiveness [p.6]。
- 作者认为条件 law 的 trivial cases 来自 precondition 对分布的 skew，应调查实际被测用例中 trivial 的比例，最好的办法是用自定义 generator 取代条件 [p.3][p.7]。
- 选择 random testing：作者列出理由，许多 adequacy criteria 需对 Haskell 重新解释，度量路径覆盖需修改 compiler，为特定路径生成数据需 constraint solving；there is no clear reason to believe 为 Haskell 自动化系统化测试方法会产生更好结果；又因 fine grain，作者 may expect random testing 特别 well [p.9]。
- 作者认为这些 old techniques 的组合对 Haskell works extremely well，理由是 functional nature 允许 local and fine-grained properties [p.11]；作者还相信其控制 size 的方法 much superior to Maurer 的做法 [p.10]。

## 5. 作者陈述的局限与前提

- 只能测试在 Haskell 内可表达且可观察的 properties，作者称这是上述 lightweight 实现决定带来的 cost；作者写道很难说清一种测试方法检出故障的有效性 [p.1]。
- 作者说所举 reverse 的 laws 只对 finite、total 的值成立，并约定除特别说明外只量化 completely defined finite values [p.2]；多态 law 须固定到 monomorphic 类型才能测试，如 `+` 对 Int 结合、对 Double 不结合 [p.2]；Lava 中被测 circuits 的类型也须固定 [p.8]。
- 含无穷结构的 property 须改写为可计算形式（如比较 `take n` 的前缀）；作者称一般而言如何陈述并执行含 bottom 的结构的 properties 并不清楚 [p.3]。只能测试 computable properties，无法在 test result 中观察 non-termination，因此不能测试 `reverse (xs++undefined) == undefined`；作者称 Haskell 标准没有让程序作此观察的办法，某些扩展可以 [p.10]。
- size 的概念对任意递归数据类型 hard even to define，限制 size 的责任交给 generator 作者 [p.4]；user-defined types 的 `Arbitrary`、`Coarbitrary` 实例由用户编写 [pp.4–5]。
- QuickCheck 不度量 test coverage，由用户调查 test data 分布并判断测试是否足够；作者说不能强制程序员这样做，不这样做的人 risks gaining a false sense of security [p.11]。
- 因 bind 拆分随机种子，`Gen` 不满足 monad 的第一定律 `return x >>= f = f x`；作者说按结果分布 morally 成立 [p.10]。

## 6. 关键术语

- property [p.2]：作者把 law 表示为 Haskell function，对每个参数都返回 True 时 property 成立；quickCheck 在随机参数上检查它。
- `Arbitrary` / `Gen` [p.3]：Arbitrary 是 type class，若能生成某类型的任意元素，则该类型是其 instance；`Gen a` 是代表类型 a 的 generator 的抽象类型。
- conditional law / `==>` [pp.2–3]：用 implication combinator 表示只在条件成立时才成立的 law，结果类型为 Property；不满足条件的候选被丢弃。
- size bound / `sized` [p.4]：generator 可访问的 Int 参数，如何解释由 generator 作者决定。
- oracle problem [p.9]：判断一个测试是否通过的问题；作者说可与另一版本的输出比较，或用 executable specification。
- test adequacy criterion [p.9]：系统化测试中先定义、再据以生成用例的准则，例如每个 reachable statement 至少在一个测试中被执行。
