# J7 MacIver & Donaldson, 2020. Test-Case Reduction via Test-Case Generation: Insights from the Hypothesis Reducer. ECOOP 2020（LIPIcs 166, Tool Insights Paper）
版本：published；J7 文件为 ECOOP 2020 正式版（CC-BY）；第 1–25 页全读（第 14–21 页实验表为主），第 26 页起参考文献略过

## 1. 问题与作者主张
- 作者指出随机生成的测试用例往往又大又乱，需要 test-case reduction；property-based testing 库里每种生成类型通常都要各自的 reducer [p.1]。
- 作者提出 internal reduction：不在生成出的测试用例上做缩减，而是在生成时消耗的随机选择序列（choice sequence）上缩减，通过不断重新生成更小、更简单且仍触发目标性质的用例来缩减 [p.1]。
- 作者主张两点优势：每个生成器都"免费"带有缩减；因为靠重新生成，任何缩减后的用例都是"本来可能被生成的"，从而缓解 test-case validity problem [p.2]。
- 作者明确说缩减质量或性能不在主要优势之内；Hypothesis 的结果比其他 property-based testing 库略好但可能慢不少 [p.2]。
- 作者把缩减形式化为在 choice sequence 上的 shortlex optimization [p.2]。

## 2. 方法
- 基本框架：用户给定 interestingness test（通常是触发某个 bug）和一个已知 interesting 的用例；reducer 对应一个 reduction order（全序），目标是找到该序下最小的 interesting 用例；实践中的 reducer 只是局部极小化，按 reduction pass 反复变换直到没有 pass 能再缩 [p.3]。
- 随机生成器被视为确定性函数，唯一的非确定性来源是 PRNG 的二进制选择；生成器可看作 choice sequence 的 parser，序列过短视为解析错误 [p.3-4]。
- shortlex 序：序列 s 比 t 小，当 |s| < |t|，或长度相同且字典序更小；选字典序是因为对应生成的"时间顺序"，先做的决定影响更大 [p.4-5]。
- 实现：Hypothesis 5.15.1 的 reducer 含 15 个 pass（6 个删除连续区间，1 个用子区间替换，1 个用全零序列替换，4 个纯字典序缩减，3 个组合型）[p.7]。
- generator-directed reduction：通过插桩 draw 调用记录每次 draw 对应的 choice sequence 区间，相当于用生成器本身作 parser 实现类似 HDD 的结构信息，把候选变换由 O(n^3) 降到 O(n) [p.8-9]。
- Generator / Reducer co-design：浮点生成器为让字典序缩减得到"看起来更简单"的浮点数（如缩到 1.0 而非 5e-324）做了专门处理；列表生成器按"每个元素前抛一个继续/停止比特"设计，使删除一个元素只需删除一段连续区间 [p.10-11]。

## 3. 数据与设置
- RQ1 最终用例大小、RQ2 缩减成本、RQ3 经生成器的额外开销；主要度量为 SUT 调用次数与生成器调用次数，而非 wall clock time [p.11]。
- 案例：用改过的 Csmith 生成 C 程序触发旧版 gcc/clang 的 bug；自写 Python 程序生成器对 yapf 与 black 做差分测试；SymPy（经 TSTL）；复现 SmartCheck 的五个合成基准（bound5、binheap、calculator、parser、reverse）[p.11-12, p.20]。
- Csmith 与 Python 各取 200 条能触发 bug 的 choice sequence，长度上限 8KB（Hypothesis 默认）；对照 C-Reduce 与 Picire（delta debugging）[p.12-13]。
- 对 C-Reduce 与 Picire 需自行定义 validity oracle（带警告检查的编译加 UBSan 运行），而 Hypothesis 经 Csmith 重新生成，按构造无 undefined behaviour [p.13]。
- 大小以格式化后字节数计（C 用 clang-format 并去掉注释，Python 用 black）[p.14]。
- SymPy：初始 3000 个失败用例，去除 flaky 后 2930 个，分布于 33 种错误，平均长度 64.5；超过两秒的单步用例被剔除 [p.19]。

## 4. 结果
- Figure 1：Csmith 的 choice sequence 长度与输出大小的 Pearson 相关系数为 0.73，作者称长度是输出大小的强但不完美的预测量 [p.4]。
- Figure 8（平均格式化字节数，Csmith / Python）：无缩减 1963.9 / 417.2；C-Reduce 120.0 / 70.9；Hypothesis 812.3 / 71.8；Picire 345.09 / 75.7。Python 上三者差异不显著（阈值 0.05）；Csmith 上差异均显著 [p.14]。
- Csmith 上 Hypothesis 的缩减结果明显大于 C-Reduce 与 Picire；原因之一是 Csmith 固定样板代码使下限为 410 字节，C-Reduce 与 Picire 可缩到空文件或 14 字节的 main；按该基线调整后 Hypothesis 平均约 402 字节，Picire 约 331 字节，差异仍显著但"更合理" [p.15]。
- 作者称缩减结果必须包含 Csmith 总会生成的特征（变量总被初始化、函数总被预声明等）；同时 Hypothesis 的结果不会出现 C-Reduce 产生的可疑 printf 多余参数 [p.16]。
- Figure 12（SUT 调用次数，Csmith / Python）：C-Reduce 3968.0 / 863.3；Hypothesis 762.0 / 1284.565；Picire 3138.9 / 529.23。作者称 Csmith 上 Hypothesis 以 SUT 调用计约比 Picire 快四倍，格式化例子上约慢 50% [p.17-18]。
- RQ3：生成器调用与 SUT 调用之比的几何平均 95% 置信区间，Csmith 为 2.78–2.94，Python 为 1.21–1.30 [p.18]。
- SymPy：Hypothesis 的 SUT 调用数是 delta debugging 的 20.6 倍（95% 置信 20.3–21），所得用例大小为后者的 83%（82%–84%）；作者称"相对昂贵而收益有限" [p.19]。作者引用 [9]：加入 normalization pass 后耗时约三十倍、用例约为不加时的 55% [p.19]。
- 合成基准（Figure 13，平均缩减后大小，Hypothesis / QuickCheck / SmartCheck）：binheap 9.02 / 9.00 / 9.42；bound5 2.08 / 11.30 / 6.02；calculator 5.00 / 5.11 / 5.00；parser 3.31 / 3.99 / 4.08；reverse 均为 2.00 [p.20]。Figure 14（SUT 调用数，Hypothesis / QuickCheck）：binheap 170.31 / 88.22；bound5 95.13 / 1438.89；calculator 72.41 / 30.97；parser 126.50 / 34.23；reverse 50.84 / 17.68 [p.20]。作者称相对 QuickCheck 成本高 2–3 倍 [p.21]。
- 作者在 binheap 基准里加了不允许无效堆的前提条件，因为注意到 SmartCheck 的性能很大程度来自快速缩到小而无效的堆（validity problem 的实例）[p.20]。

## 5. 作者陈述的局限
- 主要威胁是结果的可推广性：起点用例都不算大（默认上限 8KB），作者预期大规模用例会遇到局部极小等新困难 [p.21]。
- 实验结果仅限于 Hypothesis 这一实现，且该 reducer 经过大量工程投入，结果不能说明有多少可行性只来自工程投入 [p.22]。
- 缩减结果不可能小于生成器能产出的最小用例；生成器作为"更严的 validity oracle"导致 Csmith 上结果偏大 [p.15]。
- 作者不建议在值得投入大量工程做专用 reducer 的场合用 internal reduction [p.25]。
- SymPy 实验中剔除了慢用例与 flaky 用例，作者承认这可能影响结果的一般性 [p.19]。

## 6. 原文摘录
- "ensuring that any reduced test case is one that could in principle have been generated" [p.1]
- "The ﬁnal reduced test case is constructed as if the generator had been implausibly lucky and produced a small and readable test case by chance." [p.2]
- "Note that reduction quality or performance are not included among the major advantages of internal reduction." [p.2]
- "the minimum size of the reduced test cannot be lower than the smallest test the generator can produce." [p.15]
- "There is no straightforward way to derive an oracle for whether something could be generated" [p.23]
- "Hypothesis is reducing against a harder validity oracle: It has to produce an interesting test case that Csmith could have generated" [p.15]

## 7. 对本库的可用点（笔记者推断）
- 缩减失败用例（电池层）：电池的约 300 个用例由"事实包 x 模板 x 辖区安排 x 时点"组合生成，一旦某不变量失败，报告的是整个大用例。可把生成器写成对"选择序列"（选了哪个事实包、哪个模板、哪些辖区、哪个时点、各金额档位）的确定性解析，缩减时在选择序列上做删除与置零再重新生成，这样缩减后的用例仍是电池本来就能生成的合法用例，规避论文所称的 validity problem（层：battery / 失败诊断）。
- 缩减的 interestingness test 要定死：例如"同一不变量名、同一规则 id 仍失败"。论文在 SymPy 里按错误类型加行号区分失败，并剔除 flaky 用例 [p.19]；本库引擎确定性，无 flakiness 问题，但仍需把"同一个缺陷"定义为 (不变量, 规则) 对，否则缩减会漂移到另一个缺陷（层：battery）。
- 缩减顺序：论文用 shortlex（先少选择，再字典序小）[p.4-5]。对本库可对应为"先少辖区/少收入类型，再小金额档位、再靠前的时点"，输出最小反例供人工核对可行性，与"人类只检查可行性"的分工一致（层：battery 输出）。
- 浮点与金额的"看起来简单"：论文说明按位表示会缩到 5e-324 之类病态值，需专门设计使其缩到 1.0 [p.10]。本库金额应从少数"整齐值"档位（如 1、100、边界值）里选，而非随机浮点，缩减结果才可读（层：事实包设计）。
- 不能修复指标作弊：缩减只在已发现失败后起作用，不改变"哪些不变量被检查"。对"把容差放宽、把一条规则宣告为 silent by construction"这类问题，论文没有提供对策（层：评测治理）。
- 论文的 validity 论点可借用到"规则 fired 覆盖"：缩减出的用例必须能被生成器生成，本库的生成器因此成为"合法输入"的唯一定义，其合法性应单独被检查（例如检查生成器是否能产出 fact pack 中不存在的阈值邻域）（层：battery 生成器）。
- 不适用：论文关注的是缩减已有失败，不涉及测试充分性或 oracle 问题；其评测对象是编译器、格式化器与符号计算库，没有税法条款或带引文的输出；实验仅在 Hypothesis 上，且起点用例不大（8KB 上限）[p.21]。本库用例规模较小，缩减的收益主要是可读性，不是调试规模。
