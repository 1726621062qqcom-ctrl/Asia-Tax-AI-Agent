# L13 Gligoric, Eloussi, Marinov, 2015. Practical Regression Test Selection with Dynamic File Dependencies. ISSTA 2015, 211–222
版本：author（作者版）；L13_Gligoric2015_Ekstazi_author.pdf；第 1–10 页全读（第 6 页 Figure 4 的逐项数据略读），第 11–12 页参考文献略过

## 1. 问题与作者主张
- 作者指出回归测试选择（RTS，只运行受改动影响的测试子集）三十多年前就已提出，但除 Google 的 TAP 系统（只在项目之间做选择）外并未被实践广泛采用 [p.1]。
- 作者主张：要提高 RTS 被采用的可能，应把一个轻量的 RTS 技术接入已被广泛使用的测试框架（如 JUnit）；采用门槛是只改一处构建脚本 [p.1-2]。
- 作者称评价 RTS 的关键应是端到端时间（开发者从启动测试套件到全部结果出来所见的时间，含分析、执行、收集三个阶段），而不是被选测试的数量 [p.2]。
- 作者提出 Ekstazi：以"文件"为粒度的动态依赖，记录每个测试实体运行时用到的文件及其校验和，若所依赖文件都没变就不重跑；不需要与版本控制系统集成，也不显式比较新旧版本 [p.1-2]。
- 作者称其安全性（不漏掉受影响的测试）来自已证明的"基于类依赖的 RTS"与"基于文件依赖的部分构建"的安全性，但没有对 Ekstazi 本身给出形式证明 [p.2-3]。

## 2. 方法
- RTS 的三个阶段：分析（A）选出要跑的测试；执行（E）运行；收集（C）收集本次运行的依赖信息供下次使用 [p.2-3]。
- 收集：对每个测试实体（测试方法或测试类）保存它在执行中用到的所有文件的名称与校验和（每个实体一个"依赖文件"）。文件包括可执行代码（.class）与外部资源（配置文件等）；既记录被读或写的文件，也记录尝试访问但不存在的文件，这些文件以后若出现，行为可能改变 [p.2-4]。
- 分析：对每个测试实体检查其依赖文件的校验和是否都未变；全未变则不选；没有依赖信息的新测试实体一律选中，首次运行时所有实体都被选中 [p.3]。分析不需要旧版本，只需要旧校验和 [p.3, p.9]。
- 粒度：选择粒度（按方法或按类选测试）与依赖粒度（Ekstazi 为文件/类，传统技术如 FaultTracer 为方法或扩展控制流图的边）区别开；默认是按类选择并开启智能校验和 [p.2-3, p.7]。
- 智能校验和：对 .class 文件忽略调试信息、编译期注解等部分再算校验和，这使 A、C 阶段变慢，但使 E 阶段选中的测试更少 [p.5]。
- 两种集成方式：紧密集成（框架照常发现全部测试，Ekstazi 逐个判断是否运行）与松散集成（先生成排除列表）；执行与收集可一遍完成（AEC），也可先只跑 AE，再在另一遍（或并行）收集依赖 [p.3-4]。
- 插桩：用动态字节码插桩监测 java.io 的文件访问与类加载，覆盖构造器、静态初始化、静态方法、静态字段访问、类字面量、反射、invokeinterface 七类点；对运行时动态生成的类不追踪，因为它只会随生成它的代码变化而变化 [p.4]。
- 其他细节：构造器与 setUp 的依赖附加到每个测试方法上；JUnit 3 只支持按方法选择，JUnit 4 有自定义运行器时只支持按类选择；遇到不支持的情形就不做选择，等同 RetestAll [p.5]。

## 3. 数据与设置
- 32 个开源 Java 项目、615 个修订版本、共 4,937,189 行代码；每个项目取最近可构建版本之前的 20 个修订；项目规模 7,389 至 920,208 行，测试方法 83 至 641,534 个，全部测试的运行时间 8 至 2,565 秒；以不到一分钟为界分短时与长时测试套件 [p.2, p.5-6]。
- 项目由三名不了解研究的本科生挑选：自 Apache、GitHub、GoogleCode；要求最新版本可构建、至少 100 个 JUnit 测试、用 Ant 或 Maven、用 SVN 或 Git；约 100 个候选中三分之二被排除 [p.5]。
- 每个修订版本跑三种场景：RetestAll（不用 Ekstazi 全部运行）、AEC（含收集）、AE（不含收集）；测量开发者实际使用的构建命令（如 mvn test）的时间 [p.6]。
- 基线与对照：RetestAll；FaultTracer（基于细粒度依赖的 RTS 研究工具，当时唯一公开可用的）[p.8, p.9]。
- 指标：选中的测试实体比例；端到端时间占 RetestAll 的比例，逐修订计算后求平均 [p.7]。
- 机器：4 核 1.6 GHz Intel i7、4GB 内存、Ubuntu 12.04；三个 Oracle Java 版本 [p.5]。

## 4. 结果
- 选中比例：Ekstazi 选中的测试实体占 RetestAll 的 5% 到 38%；AEC 时间占 9% 到 138%（即最差慢了 38%）；AE 时间占 7% 到 99% [p.7]。全部项目平均，AEC 时间为 RetestAll 的 68%，AE 为 53%；只看长时测试套件，AEC 为 46%，AE 为 34% [p.7]。全部变慢的情形都出现在短时测试套件的项目中 [p.7]。摘要称端到端时间平均减少 32%、长时套件减少 54% [p.1]；引言称收集阶段单独离线进行时，平均减少 47%，长时套件 66% [p.2]。
- Cucumber 的例子：平均选中 12% 的测试实体，但时间为 RetestAll 的 99%（不计 C 阶段为 76%），几乎没有收益 [p.7]。
- 在选中几乎所有测试的修订上，Ekstazi 因分析与收集开销预期比 RetestAll 慢；每个项目的首个修订必选全部测试并收集依赖，也预期更慢 [p.7]。
- 智能校验和：平均而言并在多数情形下既减少选中数也减少时间；也有若干情形无差别或时间稍增，原因是这些项目的最近 20 个修订中没有只改调试信息的修订；作者人工检查发现还可改进（只在注解顺序上不同的 .class 文件可安全忽略）[p.7-8]。
- 选择粒度：按类选择平均并在多数情形下改善 AEC 与 AE 时间，作者据此建议按类选择为默认；按方法选择使 A、C 阶段更慢；Guava 因测试方法极多，按方法选择会产生海量依赖文件、可能超过文件系统限制，被排除在该比较之外 [p.8]。
- 与 FaultTracer 比较：Ekstazi 的端到端时间远低于 FaultTracer，尽管 Ekstazi 选中更多测试；FaultTracer 平均比 RetestAll 还慢 [p.8]。FaultTracer 有八项限制（须为 Eclipse 项目、单模块、不追踪外部文件、需要新旧源码、不追踪反射、不选新增测试、不检测测试代码变化、不能忽略注解变化），因此多数项目被排除，其中 15 个项目是多模块 [p.8]。多数情形 Ekstazi 选中的测试是 FaultTracer 的超集；少数情形选得更少，原因是智能校验和和忽略字节码层看不见的源码改动 [p.8]。CommonsMath 上 FaultTracer 收集依赖一小时后被停止 [p.9]。
- Apache CXF 案例（未参与评测）：Ekstazi 集成后 189 个修订，测试执行约 54 小时，RetestAll 约 148 小时，快 2.74 倍 [p.8]。Ekstazi 已进入 Apache Camel、Commons Math、CXF 的主仓库 [p.2, p.10]。
- 讨论：粗粒度依赖可以更快——细粒度依赖使分析要解析并比较新旧两版、收集也更贵 [p.9]；稀疏收集（每 n 个修订收集一次）只要分析对比的是最近一次收集依赖时的版本，就仍然安全，但选择更不精确 [p.9]。RTS 与并行执行互补，不互相取代；评测中四个项目默认已用全部核心 [p.9]。

## 5. 作者陈述的局限
- 外部：项目未必有代表性；每个项目只取 20 个修订，结果可能随修订段不同而不同；结果在单台机器上取得，只在另一台机器上做了少量实验，加速比相近、绝对时间不同 [p.9]。
- 内部：实现可能有缺陷；作者做了代码审查、小例子测试和人工检查若干结果 [p.9]。
- 构造：只与 FaultTracer 比较，因为它是当时唯一公开可用的 RTS 工具 [p.9]。
- 对非确定性：Ekstazi 只收集单次运行的依赖；如果某一次未观察到的运行里依赖不同，测试不会被选中，这是 RTS 通常的做法，因为收集所有可能运行的依赖代价很高 [p.9]。
- 安全性没有形式证明，留作未来工作 [p.3]。
- 目前除文件外不特别支持其他依赖（如数据库、网络服务）[p.10]；参数化测试被视为单个测试，取各输入的依赖并集 [p.9]。
- 短时测试套件（不到一分钟）上可能变慢 [p.7]。

## 6. 原文摘录
- "A test need not be run in the new revision if none of its dependent ﬁles changed." [p.2]
- "Ekstazi technique is safe for any code change and any change on the ﬁle system." [p.3]
- "Moreover, Ekstazi tracks even ﬁles that were attempted to be accessed but did not exist; if those ﬁles are added later, the behavior can change." [p.4]
- "Our insight is to view RTS as memoization: if none of the dependent ﬁles for some test changed, then the test need not be run." [p.10]
- "Ekstazi collects dependencies for a single run and guarantees that the test will be selected if any of its dependencies changes." [p.9]
- "it simply oﬀers no test selection and runs all the tests, as RetestAll." [p.5]

## 7. 对本库的可用点（笔记者推断）
- §5 "改动后按影响面挑选要重跑的案例"：本库计划的"规则在哪些案例里生效的对照表 + `search.py impact`"是方法级/规则级的依赖，对应论文中的细粒度依赖；论文的结论是粗粒度依赖（文件）的端到端成本更低，但选中更多（p.8-9）。本库可用同样思路做第二路：为每个案例（或每个检查）记录它读取过的文件（`official/` 下的条款、参数表、规则文件、`data.gold`）及其内容哈希，改动后只重跑所依赖文件的哈希变了的案例。这不需要版本控制，也不需要旧版本（p.3），与 §5 的"版本指纹"可共用。
- 依赖需要动态收集而不是靠人维护：论文用插桩收集实际访问的文件。本库对应在引擎读取参数表、条款文件的出口处（唯一的加载函数）记录文件名与哈希，每个案例运行后落盘一个"依赖文件"（每实体一个文件，p.4）。这样不会漏掉间接依赖。
- 安全性边界：论文强调记录"尝试访问但不存在"的文件，因为文件将来出现会改变行为（p.4）。本库的类比是"按日期查参数、查不到时回退"：新增一条更晚生效的参数行不是改了旧文件而是添加，若参数表是单个文件，其哈希会变，粒度过粗；若按条款/年份拆文件，应记录"查询了但无结果"的键。需要在设计依赖粒度时处理，论文没有此类数据库查找的先例（p.10 仅说明对数据库依赖无特别支持）。
- 动态生成的内容不追踪（p.4）：本库中由 SMT 或程序生成的衍生表要追踪其生成输入而不是产物，否则产物改动被当作原因。
- 必选情形：论文中没有依赖信息的新测试一律选中、首次运行全选（p.3）。对应 §5：新增案例、新增规则、依赖记录缺失或损坏时必须全跑；"快"级别不应因为依赖记录缺失而默默跳过。
- 与门禁的关系：RTS 只能用于"快/中"级；"全"级（收工前）应不依赖选择，跑全部，用来发现依赖记录本身的错误。论文承认安全性没有形式证明（p.3），且对非确定性的依赖只看单次运行（p.9）；这正是 C 层不稳定检查必须先通过的理由——引擎不稳定时依赖记录不可信。可以用 L9–L11 的打乱顺序运行结果核对：依赖记录是否对顺序不敏感。
- 评测指标：论文强调端到端时间（含分析与收集），而不是选中数（p.2）。本库度量选择机制时也应记录选择开销与收集开销（`seconds` 字段分阶段），否则会高估收益；论文发现短时套件（不足一分钟）可能反而变慢（p.7），本库"快"级目标约 5 分钟，需要实际测出是否值得选择。
- 稀疏收集（每 n 次收集一次，p.9）可借鉴到"中"级，但分析需对比的是最近一次收集时的版本。
- 不适用：论文的依赖来自 JVM 类加载与 java.io 访问，本库是 Python，且规则在数据文件而非代码里；论文数据（平均省 32%、长时套件省 54%）基于 Java 开源项目的测试套件，不能迁移为本库的预期收益。论文也没有涉及"案例的期望值（官方标签）变化"，这类改动需要把标签文件列为依赖。
