# L9 Luo, Hariri, Eloussi, Marinov, 2014. An Empirical Analysis of Flaky Tests. FSE 2014, 643–653
版本：author（作者版）；L9_Luo2014_FlakyTests_author.pdf；第 1–10 页全读，第 11 页参考文献略过

## 1. 问题与作者主张
- 作者指出回归测试的一个关键假设是测试结果确定：未改动的测试对同一被测代码应当总通过或总失败；"flaky"（不稳定）测试的结果对同一软件版本是非确定的，使人难以依赖测试结果 [p.1]。
- 作者称这是第一项对不稳定测试的大规模研究：分析 51 个开源项目里 201 个可能修复了不稳定测试的提交，回答三个问题——常见根因、如何使其暴露失败、常见修复策略 [p.1-2]。
- 作者指出此前少数工作只关注"测试顺序依赖"这一类，本文覆盖全部类别 [p.2]。
- 作者认为当时常用的做法（失败后重跑若干次，任一次通过即判通过；或把测试排除出套件）只是"workaround"，不处理根因，浪费机器资源或降低测试套件效力 [p.1]。
- 作者主张：没有对所有类别通用的万能办法，但有足够宽的类别可以做自动化的暴露、调试与修复 [p.10]。

## 2. 方法
- 从 Apache 软件基金会中央 SVN 库取全部提交历史，在提交信息里搜关键词 "intermit" 与 "flak"，得 1,129 条；选提交而不是从缺陷报告出发，理由是有的修复从未进缺陷库，有的报告未修复 [p.2-3]。
- 过滤阶段：两位作者分别人工检查每条，再合并，判定是否关于不稳定测试、是否修复一个不同的不稳定测试（LDFFT 提交）；得 855 条相关、486 条 LDFFT [p.3]。
- 分析阶段：项目按 LDFFT 数分为小（少于 6）与大（不少于 6）两组；小组全查，大组每项目抽三分之一，共 201 条。一位作者先查，另一位复核，回答：是否确为修复不稳定测试；根因；如何暴露；如何修复 [p.3]。
- 把根因分成 10 类，其中部分类别沿用从业者的分类，其余为作者在研究相似测试时归纳 [p.3-4]。

## 3. 数据与设置
- 对象：Apache 基金会的项目，至少 51 个（共 153 个顶层项目）含有不稳定测试；语言有 Java、C/C++、Scala、Python、C#、Ruby 等；这些项目合计约 2,065 万行代码；486 个 LDFFT 提交里 298 个有缺陷报告 [p.3-4]。
- Table 3 中 LDFFT 提交数最多的项目：HBase 72、ActiveMQ 68、Hadoop 56、Derby 49 [p.4]。
- 201 个被检查提交中 161 个能确定根因，40 个难归类（其中 7 个修的是确定性缺陷，6 个并未修不稳定测试，27 个难以理解）[p.6]。
- 指标：各根因类别的提交数与比例；暴露方式的可行比例；各修复策略的数量及是否彻底消除不稳定。

## 4. 结果
- 根因分布（161 个）：Async Wait 74（45%）、Concurrency 32（20%）、Test Order Dependency 19（12%），前三类合计 77%；其余 Resource Leak 11、Network 10、Time 5、IO 4、Randomness 4、Floating Point 3、Unordered Collections 1 [p.3-5]。
- Test Order Dependency 的定义：测试结果取决于运行顺序，原因是共享状态（内存静态字段，或文件、数据库等外部资源）没有正确设置或清理；一个测试先跑会破坏另一个（polluter），或一个测试依赖未运行的"setup"测试 [p.5]。
- 引入时间：161 个中 126 个从首次写入就不稳定，23 个后来才变得不稳定，12 个难判断；后来变得不稳定的两个原因是新增测试破坏隔离，与测试代码改动 [p.6]。
- 平台：154/161（96%）与平台无关；7 个需要特定平台（4 个特定操作系统、2 个特定浏览器、1 个特定 JRE）[p.6]。
- Async Wait：25/74（34%）用带时间延迟的 sleep 或 waitFor 控制次序，改延迟即可暴露；63/74（85%）不依赖外部资源且只涉及一个次序 [p.6-7]。
- Concurrency：32 个中 13 个涉及两个以上线程，但全部可简化到至多两个线程；31/32（97%）不依赖外部资源 [p.7]。
- Test Order Dependency 的依赖来源：测试中的静态字段 3/19，被测代码中的静态字段 6/19，外部依赖 10/19；前两类可以通过记录并比较对象状态暴露，外部依赖需要建模外部环境或用不同顺序重跑 [p.7]。
- 修复：Async Wait 中 42/74（57%）用 waitFor，其中 23/42（55%）彻底消除不稳定，其余只降低概率；20/74（27%）用 sleep，全部只降低概率；waitFor 平均等待 13.04 秒，sleep 平均 1.52 秒 [p.7-8]。
- Concurrency 的修复全部彻底消除不稳定：加锁 10/32（31%）、使执行确定 8/32（25%）、改守卫条件 3/32（9%）、改断言 3/32（9%）[p.8]。
- Test Order Dependency 的修复全部彻底消除不稳定：设置或清理状态 14/19（74%）、去除依赖 3/19（16%）、合并测试 2/19（10%）[p.9]。
- 其他类别的修复建议：Randomness 应控制随机种子，使每次运行可复现且种子可在运行间变化；Unordered Collections 不应假定集合的遍历顺序；Floating Point 应使断言尽量不依赖浮点结果 [p.9]。
- 38/161（24%）的修复同时改了被测代码，作者称其中多数（94%，见 Table 1 F.12）修的是被测代码的缺陷 [p.2, p.9]。
- 重跑的局限：当结果改变的概率很低时，重跑几次可能不足以暴露；重跑也耗时 [p.6]。
- 文中报告 Google 的 TAP 系统过去 15 个月平均每天 160 万次测试失败，其中 7.3 万次（4.56%）由不稳定测试引起；该数来自私人通信 [p.1]。

## 5. 作者陈述的局限
- 只研究了 Apache 项目，其中少有移动应用与 GUI 测试，平台无关等结论对这类项目可能不适用 [p.10]。
- 只用两个关键词检索提交信息，召回没有保证，可能漏掉用 "race"、"stall"、"fail" 等词描述的修复；只研究已修复的测试，漏掉只在缺陷报告里、从未修复的 [p.10]。
- 人工标注可能有误，过滤阶段有少量假阳性，作者用两人独立检查来减少 [p.10]。
- 关于 Concurrency 修复全部彻底这一发现与 Lu 等人的结论看似矛盾，作者说可能是方法不同（只取每个测试的最后一次提交，可能漏掉不完整的修复）[p.8-9]。

## 6. 原文摘录
- "An important assumption of regression testing is that test outcomes are deterministic: an unmodiﬁed test is expected to either always pass or always fail for the same code under test." [p.1]
- "This problem arises when the tests depend on a shared state that is not properly setup or cleaned." [p.5]
- "In principle, all tests in a test suite should be properly isolated and independent of one another; then, the order in which the tests are run should not aﬀect their outcomes." [p.5]
- "To avoid/ﬁx ﬂakiness due to randomness, the developers should control the seed of the random generator such that each individual run can be reproduced yet the seed can be varied across runs." [p.9]
- "In general, a good programming practice is to write tests that do not assume any speciﬁc ordering on collections unless an explicit convention is enforced on the used data structure." [p.9]
- "When the probability for a ﬂaky test to change its outcome is low, rerunning it a few times may not be enough to manifest that it can change the outcome." [p.6]

## 7. 对本库的可用点（笔记者推断）
- C 层"不稳定检查"的病因清单：论文的 10 类根因里，与本库相关的是 Test Order Dependency（共享状态）、Randomness（种子）、Unordered Collections（集合遍历顺序，对应 Python 的 set/dict 与哈希种子）、Time（对应"今天"这类系统时间）、IO（文件）。Async Wait 与 Concurrency 本库暂不适用，除非将来并行跑案例。2026-10-09 的缓存-顺序缺陷属 Test Order Dependency 的"被测代码中的共享状态"类（模块级缓存）。
- 论文区分：顺序依赖里 3+6 个来自内存静态字段，可通过比对状态暴露，10 个来自外部环境（文件、端口），需要换顺序重跑才暴露 [p.7]。对应 §2 C 层"打乱顺序、清空缓存、换哈希种子重跑"：本库的外部状态是 `official/` 的文件与 `out/` 目录，也要纳入"清空"范围，而不止进程内缓存。
- 论文指出重跑几次可能暴露不了低概率的不稳定 [p.6]。本库引擎若是确定的，则不稳定应当是 0 概率事件，一次打乱就应暴露；门禁"不稳定项数大于 0 即阻断"（§4）与论文把不稳定视为缺陷（可能掩盖真缺陷，F.12）一致，不应像 Google 那样重跑任一次通过即放行。
- 修复经验：74% 的顺序依赖用"测试前设置、测试后清理状态"修复 [p.9]。本库对应：每个检查开头显式重置缓存，而不是依赖前一个检查的残留。
- 随机性：论文建议控制种子且可在运行间变化 [p.9]。本库 §5 结果格式的 `version` 字段可再记录本次使用的哈希种子与打乱顺序的种子，以便复现失败。
- 不适用或冲突：论文研究的是 Java/C++ 单元测试的不稳定，数据来自 Apache 项目的提交信息，4.56% 的 Google 数字是私人通信，不能当作本库的先验；论文不涉及"期望值随资料更新而过时"这类不是非确定性的问题，那类问题归 §5 总控而不是不稳定检查。
