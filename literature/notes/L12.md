# L12 Zeller, Hildebrandt, 2002. Simplifying and Isolating Failure-Inducing Input. IEEE Transactions on Software Engineering 28(2), 183–200
版本：author（作者机构页的网络档案副本，TSE 版式，页码 1–17 为 PDF 页）；L12_Zeller2002_DeltaDebugging_author.pdf；第 1–16 页全读（第 11、15 页的表格数字因文本抽取错位只取可辨认部分，第 7 页代码清单略读），第 17 页为参考文献，略过。形式定义中的数学符号在文本里有乱码，定义与算法按周围文字转述

## 1. 问题与作者主张
- 给定一个使程序失败的测试用例，作者问的是：测试用例的哪些情形（circumstances）对这次失败负责 [p.1]。
- 作者提出 Delta Debugging 算法：ddmin 把失败的测试用例简化到仍产生同一失败的极小用例；dd 在已有一个通过用例与一个失败用例时，找出二者之间引发失败的差异 [p.1]。
- 作者称，据其所知此前没有人把测试用例简化自动化；教科书教人用二分法定位，但假定测试是手工做的；测试自动之后，简化与差异隔离都能自动做 [p.1]。
- 作者称在案例中，Mozilla 在 95 个用户动作后崩溃，原型自动简化为 3 个相关动作；896 行 HTML 简化为引起失败的 1 行；案例共需 139 次自动测试，在 500 MHz PC 上 35 分钟 [p.1]。
- 作者建议把自动化的测试用例简化作为自动测试的组成部分：每次测试失败，都可用 Delta Debugging 简化并隔离失败情形 [p.16]。

## 2. 方法
- 形式化：运行 r 由一组"可变情形"决定；失败运行 r_fail 与通过运行 r_pass 之间的差异是一个变化（change），可分解为若干基本变化 δ1…δn；一个测试用例是这些变化的子集，测试函数返回三种结果：通过（PASS）、复现了所关心的失败（FAIL）、结果不确定（UNRESOLVED，取自 POSIX 1003.3）[p.3]。
- 公理 4：不加任何变化的运行通过，加上全部变化的运行失败 [p.3]。
- 极小性：全局最小要检验 2^|c| 个子集，不可行；局部最小（minimal）指没有任何子集仍失败；作者采用 n-minimal 近似，目标是 1-minimal，即去掉任意单个变化失败都消失 [p.4]。
- ddmin：把当前失败用例分成 n 个互不相交的等大子集；依次规则：若某个子集 Δi 测试失败，则缩小到 Δi（reduce to subset，n 重置为 2）；否则若某个补集失败，则缩小到补集（reduce to complement，n 减 1）；否则若 n 小于变化数，则把粒度加倍（increase granularity，取 2n 与变化数的较小者）；否则结束 [p.4-6]。作者提示测试函数应记住已做过的测试以免重做 [p.5-6]。
- ddmin 的性质：返回 1-minimal 用例（命题 11）；最坏情形测试次数为 |c|²+3|c|（命题 12，文本公式乱码，摘自正文 "n2+3n"）；若只有一个引发失败的变化且包含它的用例都失败，测试次数不超过 2 log2|c|（命题 13，即二分搜索）[p.6]。
- dd（隔离）：同时维护一个失败用例 c'_fail（向下缩）与一个通过用例 c'_pass（向上扩），失败时缩小失败用例，通过时扩大通过用例，二者之差即引发失败的差异；规则在 ddmin 上增加 "increase to complement" 与 "increase to subset"，而 "increase granularity" 只在此前所有测试都为 UNRESOLVED 时才用；类似分支定界但无回溯 [p.12-13]。
- dd 的性质：返回 1-minimal 的差异（命题 16）；最坏情形与 ddmin 相同（命题 17）；若所有测试都不是 UNRESOLVED，测试次数不超过 log2|c|，且差异恰为单个变化（命题 18、推论 19）；ddmin 是 dd 的特例 [p.13]。
- 单调性假设：Delta Debugging 假定失败是单调的，一旦出现失败，再添加"撤销"性的变化不能使失败消失；作者给出 HTML 标签配对的反例，并指出需要用更高精度或领域知识检测 [p.16]。
- 精度：测试函数的 FAIL 可以只看"是否崩溃"（低精度），也可以要求回溯（backtrace）与原失败相同（高精度），后者防止简化出的用例引发的是另一个失败；作者称更高精度总会使极小用例变大 [p.10]。

## 3. 数据与设置
- 案例一：GCC 2.95.2（Intel Linux，开启优化）在 bug.c 上以致命信号崩溃，变化取为插入单个字符，通过运行是空输入；还用同一方法在 31 个 GCC 优化选项上找出阻止失败的选项（变化 = 去掉一个选项）[p.6-8]。
- 案例二：Mozilla 打印崩溃（bug #24735）：用 XLAB 捕获并重放用户动作，711 个 X 事件中只有 95 个是用户动作；另有 896 行（39,094 个字符）HTML [p.8-9]。
- 案例三：重复 Miller 的 UNIX 工具 fuzz 实验：NROFF、TROFF、FLEX、CRTPLOT、UL、UNITS，16 种 fuzz 输入（大小 10^3 至 10^6 个字符，字符范围与是否含 NUL 不同），Solaris 2.6 [p.9-10]。
- 原型 WYNOT（"Worked Yesterday, NOt Today"）；所有时间在 500 MHz Pentium III 的 Linux PC 上测得 [p.7]。
- 评测指标：测试运行次数、最终输入大小；没有统计检验 [p.7-12]。

## 4. 结果
- GCC：前两次测试把 755 个字符减到 377 与 188 个字符；再经 731 次测试（34 秒）得到 77 个字符的 1-minimal 用例 [p.6-7]。对选项，每次变化为去掉一个选项：用 7 次测试找到 -ffast-math 阻止失败，去掉它再做一次，又用 7 次找到 -fforce-addr；其余 29 个选项仍会失败 [p.8]。
- Mozilla：用户动作经 82 次测试（21 分钟）由 95 个减为 3 个（Alt+P，按下并释放鼠标键 1 于 Print 按钮）[p.8-9]；HTML 经 57 次测试由 896 行减为 1 行，再按字符减为 `<SELECT>` [p.9]。作者指出原 HTML 含多个 SELECT 标签，Delta Debugging 只返回一个 [p.9]。
- fuzz：96 次运行中工具崩溃 42 次（43%）；对 42 例做最小化，FLEX 对 2,121 个及以上非换行非 NUL 字符崩溃，UL 对 516 个及以上可打印非换行字符崩溃，UNITS 对 77 个及以上 8 位字符崩溃；CRTPLOT 对单字符 "t"、"f" 崩溃，用 24 次测试把 10^6 个字符减成这一个字符 [p.10]。FLEX 的 t16 输入经 494 次测试降到 2,122 个字符后，还要超过 10,000 次测试才能再去掉一个字符 [p.10]。
- 精度效应：NROFF 的 t1 输入由 10^3 字符，低精度下最小化到 2 个字符，高精度（要求回溯相同）则为 60 个，作者称那 2 个字符引发的是另一个失败；TROFF、FLEX 同样变大，其余三个程序不变 [p.10]。
- ddmin 的缺点：简化后的输入越大，需要的测试越多；FLEX 简化到 2,121 个字符的测试数在低精度下为 11,589 至 17,960，高精度下 34,450 至 37,454；单次测试 0.1 秒时约需 1 小时 [p.11-12]。
- 隔离相对简化：Mozilla 那行 HTML，ddmin 用 26 步简化为 `<SELECT>`，dd 用 7 次测试就把差异缩到一个字符 "<" [p.12]。作者说隔离通常比简化高效得多，但程序员需要同时记住通过用例的公共背景；如果程序运行时间与输入大小成比例，简化可能测试次数多但总运行时间低 [p.12]。
- 重做 GCC：ddmin 需 731 次测试，dd 只需 59 次，指出一个 2 字符的差异：去掉 mult 函数里对 i 的赋值，程序就不再使 GCC 崩溃 [p.14]。
- 重做 fuzz（高精度）：dd 的测试次数远少于 ddmin；除 NROFF 外，最小失败差异都是单个字符；只有 NROFF、TROFF、FLEX 有 UNRESOLVED 结果，其他程序的测试次数与输入大小成对数关系，符合命题 18 [p.14]。
- 相关工作：作者称此前的类似工作只针对特定领域，且只是对单一情形的二分搜索；dd 是先前的 ddv（作用于程序版本之间的代码变化，假定单调且不保证 1-minimal）的后继，作者建议用 dd 取代它 [p.14-15]。

## 5. 作者陈述的局限
- 假定失败单调：加上"撤销"变化可使失败消失的情形会使结果出错；检测它们不能只靠测试本身（要检验最小用例的最多 2^|c| 个超集），作者正在研究提高精度或用领域知识是否可行 [p.16]。
- 变化的分解方式是特定问题的，由使用者决定；作者建议无把握时用原子分解 [p.3]。
- 测试结果为 UNRESOLVED（如语法非法的程序）越多，所需测试越多；没有领域知识（如语法）也能工作，但有了会更高效 [p.6, p.15]。
- 多个独立的失败原因：实现只跟踪第一个失败子集，只报告一个；理由是经济，应先修复第一个再查下一个 [p.9, p.16]。
- 测试要设时限（"set an upper time bound for test cases"）[p.9]；测试次数过多时需要实用的折中，如时限、缩小到一定比例即停 [p.12]。
- 文中未专门讨论非确定性测试对算法的影响（测试结果被默认视为可重复）。

## 6. 原文摘录
- "The Delta Debugging algorithm generalizes and simpliﬁes some failing test case to a minimal test case that still produces the failure; it also isolates the difference between a passing and a failing test case." [p.1]
- "Simpliﬁcation means to make each part of the simpliﬁed test case relevant: removing any part makes the failure go away." [p.12]
- "Isolation means to ﬁnd one relevant part of the test case: removing this particular part makes the failure go away." [p.12]
- "In general, isolation is much more efﬁcient than simpliﬁcation." [p.12]
- "one will ﬁnd, though, that higher precision will always increase the size of the minimized test case." [p.10]
- "analysis disproves causality, and testing proves it." [p.16]
- "Delta Debugging assumes that failure is monotone: Once a failure occurs, one cannot make it disappear by adding more “undoing” changes." [p.16]

## 7. 对本库的可用点（笔记者推断）
- C 层"变化归因"：§2 写的"自动开关各项改动来定位"正是 dd。把"金标快照与现在相比"这一差异看成变化集：基线 = 通过运行（旧代码/旧资料库指纹/旧口径），当前 = 失败运行（快照不一致）；变化 δi = 自上次金标以来的每一项改动（代码提交、资料库文件、口径 D 编号、参数行）。dd 可输出一个 1-minimal 的"引起这一处快照变化的改动集合"，对应门禁"回归变化未能归因"（§4）。隔离版 dd 的最好情形是 log2 次测试 [p.13]，适合每次测试都要重算一遍引擎的场景。
- 测试函数的设计要抄论文的三值：PASS=快照一致，FAIL=出现要归因的那处变化，UNRESOLVED=该改动子集下引擎报错或编译不过（部分改动单独应用常常不自洽，如只改引用不改参数）。UNRESOLVED 多时 dd 退化到 n²（命题 12/17）[p.6, p.13]；故改动的分解要合理，例如把"同一口径的代码、数据、测试期望"捆成一个变化，而不是按文件逐个拆。
- 精度（FAIL 要匹配同一失败）：论文发现只看"崩溃了"会简化到另一个失败上（p.10）。对应本库：FAIL 应当是"同一个案例同一个税种的数仍与旧值不同，且差额相同"，而不是"有任何不一致"，否则归因会跑到别的变化上。需要比较的是 `subject`、`check_id` 与 `measured` 的差异，而不是整体通过与否。
- 单调性假设与本库的冲突：论文要求"撤销"变化不存在（p.16）。本库中两项改动可能相互抵消（如税率改了、基数口径也改了、净变化为零，或一项改动掩盖另一项）；此时 dd 可能返回不含真正原因的集合。对策：dd 找到集合后再用整个改动集合和余集各验证一次，并在结果里标出"可能存在相互抵消"；这一点论文没有给出办法，只说是未来工作。
- 同样可用于缓存-顺序缺陷（§2）：把"测试顺序"视为变化的一种，对一个顺序依赖的失败，dd 的隔离可以找到最小的触发序列（L10 的 k 个测试）。这与 L9–L11 的打乱检查是上下游关系：打乱发现不稳定，dd 缩小触发序列。
- 蜕变关系或变异测试失败的最小化（§3.2、§3.5）：当一个电池案例（大型集团结构）失败时，可用 ddmin 减少它的流、公司、事实，得到最小的违反 MRn 的案例，送人或进专家包时更易读。注意：减少过程会产生不合法结构（UNRESOLVED），需要用领域约束（如公司必须有所属法域）过滤，论文在未来工作中也建议用语法排除非法输入 [p.15-16]。
- 不适用：论文假定测试确定、可重复、成本低；本库全量运行要 1.5–2 小时（§5），逐次测试的 dd 在"全"级上代价高，需要用 `search.py impact` 之类先缩小候选改动集（对应 L13）。ddmin 在大输入上需上万次测试的结果（FLEX，p.11-12）说明不要对大输入做简化，而应使用 dd 的隔离。论文没有处理非确定性测试，本库要先确认引擎本身稳定（C 层不稳定项数为 0）才能运行归因。
