# J9 Inozemtseva & Holmes, 2014. Coverage Is Not Strongly Correlated with Test Suite Effectiveness. ICSE 2014
版本：author（作者版）；J9 文件为作者自存 PDF；第 1–10 页全读，参考文献略过

## 1. 问题与作者主张
- 作者指出测试集的覆盖率常被当作其发现缺陷能力的代理指标，但此前研究对二者关系的强度和性质没有共识 [p.1]。
- 作者指出以往研究的三个问题：部分研究未控制测试集规模（覆盖率随用例数增加，二者相关）；除一项外都用小型或合成程序；许多只比较"adequate"测试集（完全满足某覆盖准则），而这类测试集在实践中少见 [p.1]。
- 三个研究问题：RQ1 有效性是否与用例数相关；RQ2 忽略用例数时有效性是否与 statement、decision、modified condition 覆盖相关；RQ3 固定用例数时是否相关 [p.1]。
- 作者主张：覆盖率可用于发现测试不足的部分，但不应作为质量目标，因为它不是测试集有效性的好指标 [p.1]。

## 2. 方法
- 沿用以往研究的通用步骤：用变异工具生成有缺陷版本，从用例池中抽取生成测试集，测覆盖率，把有效性定义为被测试集检出的缺陷版本比例 [p.2]。
- 变异测试用 PIT 工具：mutant 是对原程序做小的语法改动（改常量、取反分支条件、删方法调用）得到的版本；测试集失败即"杀死"该 mutant；等价变异体（equivalent mutant）不可能被单元测试检出，被排除；作者把整套主测试集（master suite）未检出的变异体假定为等价，这会高估等价变异体数量 [p.3-4]。
- 两种有效性度量：raw kill score（检出的变异体数除以非等价变异体总数）；normalized effectiveness（检出的变异体数除以测试集所覆盖的非等价变异体数）；作者称后者像"深度"，前者像"广度"；整套主测试集两者均为 1 [p.5]。
- 测试集由对主测试集的测试方法不放回随机抽取生成，每个规模 1,000 个：3、10、30、100 个方法等，直到小于总方法数的最大值，共 31,000 个测试集 [p.4]。
- 覆盖率由 CodeCover 测量：statement、decision、modified condition coverage（MCC）；作者说明 MCC 与航电行业常用的 MC/DC 很相似，DO-178B 要求最关键软件的测试集满足 MC/DC [p.4-5]。
- 相关性用 Kendall τ（不假设线性或正态）；按 Guilford 标度：绝对值小于 0.4 为 low，0.4–0.7 为 moderate，0.7–0.9 为 high，高于 0.9 为 very high [p.5]。

## 3. 数据与设置
- 五个开源 Java 项目，约 80,000 至 724,000 行 SLOC：Apache POI、Closure Compiler、HSQLDB、JFreeChart、Joda Time；要求规模约 100,000 SLOC、约 1,000 个测试方法、Ant 构建、JUnit [p.3]。
- Table 2：总 Java SLOC 分别为 283,845 / 724,089 / 178,018 / 125,659 / 80,462；测试方法数 1,415 / 7,947 / 628 / 1,764 / 3,857；主测试集的 statement 覆盖 67 / 76 / 27 / 54 / 91 %，decision 覆盖 60 / 77 / 17 / 45 / 82 %，MC 覆盖 49 / 67 / 9 / 27 / 70 %；被假定等价的变异体占 35 / 11 / 0.4 / 21 / 11 % [p.4]。
- 同类工作对照（Table 1 共 12 项研究）：八项发现至少一种覆盖在控制规模后仍与有效性有一定相关，但多数为高度非线性，部分只在覆盖率很高时才出现；此前最大程序为 5,905 SLOC [p.2]。

## 4. 结果
- RQ1：归一化有效性对规模的回归 adjusted r^2 在 0.26 至 0.97 之间，换算 r 为 0.51 至 0.98，作者称相关为中等到非常高；非归一化的 r^2 为 0.69 至 0.99 [p.5]。
- RQ2（忽略规模）：归一化有效性与 statement / decision / MCC 覆盖的 Kendall τ，Apache POI 0.75 / 0.76 / 0.77，Closure 0.83 / 0.83 / 0.84，HSQLDB −0.35（三者相同），JFreeChart 0.50 / 0.53 / 0.53，Joda Time 0.80（三者相同）；非归一化时 HSQLDB 为 0.81 / 0.80 / 0.79，其余在 0.85 至 0.95 [p.6]。HSQLDB 的负相关说明高覆盖测试集含有大量"跑很多代码但杀不死多少变异体"的用例 [p.6]。
- RQ3（固定规模）：控制规模总是降低覆盖与有效性的相关；归一化度量下相关一般较低，非归一化下为中等；Joda Time 由 0.80 至 0.85 降到约为零，Closure 在归一化度量下同样；Apache POI 非归一化由 0.94 降到 0.46 至 0.85 [p.7]。
- 三种覆盖类型的结果相近：覆盖类型之间的 Kendall τ 为 0.92（statement/decision）、0.91（decision/MCC）、0.92（statement/MCC），Pearson 为 0.99、0.98、0.97；作者据此认为覆盖类型对相关强度影响很小 [p.8]。
- 作者观察到最大、最完整的两个测试集（Joda Time 与 Closure）相关性最弱，称这"可能表明测试集越好相关越弱" [p.8]。
- 作者结论：fixed coverage 作为质量目标不太可能产生有效的测试集；复杂的覆盖度量未必值得其测量和满足的成本；DO-178B 对 MC/DC 的要求可能增加成本而未必增加质量；他们认为 mutation score 可能是覆盖的较好替代，但称这仍是开放问题 [p.8-9]。
- 对测试生成研究者：许多测试生成技术以最大化覆盖为目标，作者称这可能不是最好的做法 [p.9]。

## 5. 作者陈述的局限
- 有效性用变异体而非真实缺陷衡量，且把主测试集未检出的变异体当作等价（最高占 35%），可能偏倚；例如开发者常测试差一错误则对应变异体更少被归为等价 [p.9]。
- Kendall τ 有并列秩时显著性的计算要作近似；最坏情形 4.6% 的比较并列，多数低几个数量级；重复测试集的影响同理被忽略 [p.9]。
- 研究的是相关性，不能就因果方向下结论 [p.9]。
- 外部效度：部分旧研究发现关系只在很高覆盖率才出现，本研究生成的测试集很少达到极高覆盖，可能漏掉这种关系；作者认为要 90% 才出现的关系对多数开发者"等同于没有关系"；未控制测试方法所属类的大小；五个项目彼此相似，均为开源，规模对工业界仍不算大 [p.9-10]。
- 后续计划：用真实缺陷验证，研究数据流覆盖，做纵向研究 [p.10]。

## 6. 原文摘录
- "coverage, while useful for identifying under-tested parts of a program, should not be used as a quality target because it is not a good indicator of test suite eﬀectiveness." [p.1]
- "Controlling for suite size always lowered the correlation between coverage and eﬀectiveness." [p.7]
- "high coverage does not indicate that a test suite is eﬀective. This means that using a ﬁxed coverage value as a quality target is unlikely to produce an eﬀective test suite." [p.8]
- "suggesting that the diﬀerent types of coverage are measuring the same thing." [p.8]
- "in many cases, the apparent relationship is largely due to the fact that high coverage suites contain more test cases." [p.8]
- "Of course, developers still want to measure the quality of their test suites, meaning they need a metric that does correlate with fault detection ability." [p.9]

## 7. 对本库的可用点（笔记者推断）
- "规则至少触发一次"这一覆盖与 statement coverage 同类：它说明代码或规则被执行过，不说明被检验过。论文结论是覆盖可用来发现测试不足的部分，不宜作为质量目标 [p.1, p.8]。对应到本库，可保留"未触发规则"清单作为发现缺口的工具，但不应再用"覆盖率达到 X"或"零缺陷"作为通过标准（层：battery 评测治理）。
- 指标作弊与 Goodhart：论文的 Joda Time 与 Closure 控制规模后相关接近零 [p.7]，说明指标与目的之间的关系可能很弱。本库把"不变量全部通过"当目标并放宽容差、把一条规则宣告 silent by construction，正是这种脱节的实例；论文没有讨论人为操纵指标，这一对应是推断。
- 用变异测试检验不变量的力度（电池层，最直接的可用点）：论文用 mutant（改常量、取反分支、删调用）度量测试集能否发现缺陷 [p.3]，并建议 mutation score 作为覆盖的替代 [p.9]。本库可对规则库做"领域变异"：改阈值（183 改 182 或 184）、翻转比较符、删一条规则、改一个税率、去掉一个引文，然后看电池的不变量与对照用例能否发现；杀不死的变异体即电池盲区。这直接回应"阈值邻域从未被检验"和"自测环路驱动到零缺陷"。
- 变异体的等价问题：论文把整个主测试集未检出的变异体假定为等价，这会高估等价变异体 [p.4]。在本库里此假定尤其危险——杀不死可能恰是因为电池太弱。应该对未杀死的变异体逐个人工判断是否真的等价（例如阈值改动在所有合法事实下输出不变），而不是自动归为等价。
- 规模混淆：论文强调覆盖与用例数相关，需在固定规模下比较 [p.1, p.7]。本库电池约 300 个用例，若比较不同电池版本的覆盖或缺陷发现，应固定用例数或采用归一化指标，否则"覆盖提高"只是用例变多。
- 归一化度量的想法：论文用"检出变异体数 / 被覆盖变异体数"衡量深度 [p.5]；本库可用"每条规则被检验的深度"（有几个阈值邻域用例、几个不变量真正依赖该规则）补充"是否触发"。
- 覆盖类型之间高度相关（τ 0.91 至 0.92）[p.8]：不同粒度的规则覆盖统计可能只是同一信息，应优先投入于不同类别的检查（变异、邻域、组合覆盖、对照算例），而非更细的"触发"统计。
- 不适用：论文研究的是 Java 单元测试的代码覆盖与变异体检出，用例池来自开发者手写；本库电池是生成式的、规则在数据层而不在代码；论文的因果结论只是相关性，且五个开源项目与税务引擎差异大；不能直接推出本库的"规则覆盖"与缺陷发现率的相关强度，需要用本库自己的变异实验测量。论文也没有给出替代 oracle 的方法。
