# J1 Mokhov, Mitchell, Peyton Jones, 2020. Build systems à la carte: Theory and practice. JFP 30, e11
版本：published；J1_Mokhov2020_BuildSystemsALaCarte.pdf；第 1–40 页读（含 §2–§7 的抽象、调度器、rebuilder、traces、实现与经验），第 43–52 页读 §8.3、8.5、8.8、9.2、9.3 与结论，其余工程小节（§8.1–8.2、8.4、8.6–8.7、8.9、§9.1）和参考文献略过

## 1. 问题与作者主张
- 作者给出一个抽象且可执行（Haskell）的框架来理解与比较 build system，把它们看作同一景观中相关的点，而不是孤立现象 [p.1]。
- 作者主张 build system 的两个深层设计选择是正交的：任务构建的顺序（scheduler）与是否重建某个任务（rebuilder），二者组合给出新的分类（Table 2）[p.2, p.28]。
- 作者主张可用该框架刻画 MAKE、SHAKE、BAZEL、BUCK、NIX、EXCEL，并重组出新系统（如 CLOUD SHAKE：suspending scheduler 加 constructive traces）[p.2, p.35]。
- 作者定义并区分 minimality（最小性）、correctness、early cutoff、dynamic dependencies、self-tracking 等性质 [p.1, p.4, p.15]。

## 2. 方法
- 词汇：store 是从 key 到 value 的映射，另含 build system 自己跨次保存的 persistent build information；task description 说明如何用依赖的最新值算出一个 key 的新值；build system 接收 task description、目标 key 与 store，返回目标及其依赖都最新的新 store [p.9]。
- Task：`newtype Task c k v = Task (forall f. c f => (k -> f v) -> f v)`；`Tasks c k v = k -> Maybe (Task c k v)`，输入 key 对应 Nothing；任务通过回调 fetch 取依赖的值 [p.9-10]。
- Build：`Tasks c k v -> k -> Store i k v -> Store i k v` [p.11]。最朴素的 busy build system 无记忆（i = ()），多个依赖者会重复计算同一 key，不满足 minimality [p.12]。
- 约束 c 对任务分类：Functor（线性依赖链）、Applicative（依赖可静态获得）、Monad（动态依赖，如 INDIRECT）、Selective（含条件分支、可静态过近似依赖）、MonadFail、MonadRandom 等 [p.13-14]。
- 静态依赖提取：对 Task Applicative 以 f = Const [k] 运行，不做实际计算即得依赖列表；动态依赖用 `track` 在具体 store 上运行并记录 (key, value) 对 [p.16-17]。
- Minimality 定义：build 至多执行每个任务一次，且仅当任务传递依赖于自上次 build 以来变化的输入时才执行 [p.4]。Correctness 定义：结果与 store 在输入键上一致，且每个非输入键的存储值等于用结果 store 重算该任务的值 `compute`；该定义假设任务描述无环 [p.15-16]。
- Scheduler（§4）：topological（预先算线性序，需要静态依赖，要求 Applicative）；restarting（任务取到未更新的依赖时中止并重启；EXCEL 用 calc chain 减少中止）；suspending（依赖未就绪时挂起当前任务去构建依赖，SHAKE、busy 采用）[p.20-22]。
- Rebuilder（§5）：dirty bit（每键一位，构建后清零；变更处传递性标脏）；verifying traces（记录上次依赖的值/哈希，不变则跳过）；constructive traces（还存结果值，可跨用户共享，对应 cloud build）；deep constructive traces（只看终端输入，不考虑中间依赖）[p.22-28]。
- Verifying step traces（SHAKE）：不存依赖哈希，改存 built 与 changed 两个时间戳以及依赖键列表，保持 minimality 与 early cutoff [p.25-26]。
- 组合：Scheduler = Rebuilder -> Build；Rebuilder = k -> v -> Task c k v -> Task (MonadState ir) k v；任何 scheduler 可与任何 rebuilder 组合得到正确的 build system [p.28-29]。

## 3. 数据与设置
- 本文为理论加经验报告，无基准实验；所有模型是可执行的，发布在 Hackage 的 build-1.0 [p.2]。
- 经验（§7）：SHAKE 约 5,000 个后续提交，CLOUD SHAKE 在 Standard Chartered 与 GHC 的 HADRIAN 构建系统中使用 [p.36, p.38-40]。

## 4. 结果
- Table 1（四个系统）：MAKE 为 Topological、Static 依赖、Minimal、无 cutoff；EXCEL 为 Restarting、Dynamic、非 Minimal、无 cutoff；SHAKE 为 Suspending、Dynamic、Minimal、有 cutoff；BAZEL 为 Restarting、Dynamic∗、非 Minimal、有 cutoff、Cloud [p.8]。
- Dynamic dependencies 使 minimality 变难；EXCEL 用保守近似：公式静态提到变更单元格、使用 INDIRECT 这类依赖不可静态见的函数、或公式本身变化时重算 [p.5]。
- Early cutoff：任务重算后结果不变就不必执行其依赖者；SHAKE 与 BAZEL 支持，MAKE 与 EXCEL 不支持 [p.6]。Collatz 序列示例：初值从 6 改为 40，序列在两步后汇合（c2 = 10 未变），可在两步后停止重算 [p.19]。
- dirty bit 可以做到 minimal，但要同时做到 early cutoff，需要"重算后值未变就清除 dirty 位且不标脏依赖者"；EXCEL 因依赖单元格已被递归标脏而难以做到，MAKE 无法在标本键为干净的同时不标依赖者为脏 [p.23]。作者也说明若要用 dirty bit 做到 minimal 加 early cutoff，则要求每次都重建所有目标，否则清除不在当前目标依赖里的键会错误地不再重建，为此引入 step traces [p.23]。
- Verifying traces 对 Applicative 任务可省略依赖键；每键只存一个 Trace 收益近乎等同于存多个，但代价是依赖变了又变回时需重建，而存全部历史 trace 则可跳过 [p.25]。
- Step traces 与 verifying traces 的一个可观察差别：Figure 7 的例子中，util.c 改后又改回，verifying traces 不重建 main.exe，step traces 会重建；作者称除构建目标子集外未发现 step traces 更弱的其他情形 [p.26]。
- Constructive traces 支持 early cutoff；deep constructive traces 不支持 early cutoff，且要求任务确定 [p.24, p.27]。
- suspending scheduler 加合适 rebuilder 给出支持动态依赖的 minimal build system；作者称其理论上最优，但仅当避免的重复工作超过挂起成本时才优于 restarting，而重复工作的代价常只占总构建成本的一小部分 [p.22]。
- Memoisation 可归约为 minimal build system，反之不行；Levenshtein 编辑距离示例中改变输入 ai 时，minimal build system 只做必要的增量重算，这是单靠 memoisation 做不到的 [p.52]。
- 经验：Standard Chartered 报告暖缓存从零构建约 5 s，最多节省 2 h [p.39]。GHC 8.8 从零构建在 Windows 上约 1 小时；提交不影响 GHC 二进制时 HADRIAN 借缓存 3 分钟完成，若修改 Stage 1 GHC 则缓存命中几乎消失；作者称体验是混合的 [p.40]。

## 5. 作者陈述的局限
- 所有讨论的 build system 仅在任务描述无环时正确；busy 在有环任务描述上无限循环 [p.16]。作者选择不处理循环依赖，指出有些框架在任务单调时支持环 [p.45]。
- 模型假设 Task 是纯函数；现实中有未跟踪依赖、非确定性与 volatile（易变）任务，三者相互作用；BUCK 的单次云查询依赖任务确定性假设 [p.43-44]。
- 需要调整 correctness 定义以适应非确定性任务与 shallow cloud build：要求值属于重算可能结果的集合 [p.16, p.43]。
- Self-tracking：用完整编程语言写任务的系统（如 SHAKE）难以比较两个任务是否相同，唯一安全做法是悲观地假设构建脚本任何变化都可能改变任意任务 [p.48]。
- 作者称自适应计算（self-adjusting computation）里的 delta 增量处理等优化在 build system 中是未来工作 [p.51]。
- 作者称模型抽象了许多工程细节（错误、并行、云实现等）；§8 讨论它们对模型的影响 [p.40]。

## 6. 原文摘录
- "A build system is minimal if it executes tasks at most once per build, and only if they transitively depend on inputs that changed since the previous build." [p.4]
- "Dynamic dependencies complicate minimality." [p.5]
- "When it executes a task and the result is unchanged from the previous build, it is unnecessary to execute the dependent tasks, and hence SHAKE can stop a build earlier." [p.6]
- "It is OK to mark too many cells as dirty; but not OK to mark too few." [p.31]
- "the only safe approach is to assume (pessimistically) that any change to the build system potentially changes any build task" [p.48]
- "Memoisation can, therefore, be reduced to a minimal build system" [p.52]

## 7. 对本库的可用点（笔记者推断）
- 把引擎写成 store/task 模型（层：分析低效）：key 可取为 (候选结构 id 的某个子结构, flow, 规则, pending 取值向量)，value 为该 flow 的税额与关联的条件结果。引擎的"固定顺序评估"对应 topological scheduler，其前提是依赖可静态给出 [p.20-21]。若某 flow 的规则是否触发取决于前一 flow 的结果（例如抵免依赖伪 flow），这就是 Monad 型动态依赖，topological 序不够；suspending scheduler 可替代固定顺序，天然处理伪 flow 与抵免间的依赖 [p.21-22]。这是推断，论文不涉及税务。
- Minimality 作为目标（层：分析低效）：引擎"强制 pending 取另一值后整图重算"以及第二次单调性重算，是 busy 加无记忆的情形（重复计算，且没有 persistent information）[p.12]。minimality 要求只重算传递依赖于被改动输入的 task；对应地，只有读取了该 pending 的 flow 及其下游需要重算，其余沿用存储值。
- 记忆化与跨候选共享（层：数据库使用不精确、分析低效）：constructive traces 以"key 加依赖哈希"索引结果，可在不同候选结构间共享，对应"相同 flow 在不同候选里被重复计算"：对 flow 的键取（规则版本、该 flow 实际读取的事实、其所依赖 pending 的取值）的哈希即可命中 [p.26-27]。论文提醒共享缓存需版本号（规则版本改变时视为所有键变化，§7.3 的 Ver 参数 [p.38]）、需声明全部产出、需避免"无关差异"（路径等）使缓存失效 [p.39]；对应本库：缓存键要包含规则库版本，且只含该 flow 真正读取的字段。
- 早停（层：分析低效）：early cutoff 的前提是比较重算前后的值；对引擎，若强制某 pending 后某 flow 的税额不变，则其下游不必重算 [p.6, p.19]。并且 verifying 的做法是比较依赖值的哈希而不是脏位，因为脏位被递归标脏后难以回退 [p.23]。这直接对应"判断某待定项是否相关"的问题：若强制取反后实体级税额不变，则该项在此实体层无关，无需对其余 pending 的 2^7 个组合再枚举。注意：此处只是类比，论文并未提供枚举组合的替代算法。
- 动态依赖与追踪（层：分析低效）：用 `track` 的方式，在一次评估中记录每个 flow 读了哪些事实、哪些 pending（读取集）[p.17]；之后"某 pending 是否相关"等价于"它是否在某 flow 的读取集中"，无需靠枚举其余组合运行两次规则。读取集随值而变（Monad），因此对条件树的短路求值会改变读取集——记录的是实际读取的条件，这与三值逻辑的 pending 传播（未读取的分支不依赖）相容，但读取集须按取值记录，不能只记一次。
- 与三值的冲突（层：局部最优）：论文的 correctness 针对确定性单值任务（一个 key 一个 value）[p.15-16]；引擎的 floor/ceiling 区间对应非单值，或者说同一 key 在不同 pending 取值下有多个值。可将"pending 取值向量"并入 key（把任务变成多个确定任务），或类比论文 §8.3 把正确性改为"值属于可能结果集合" [p.43]。论文不解决"在所有取值上求 min/max"这类优化，不提供联合代价的方法。
- 自追踪（层：数据库使用不精确）：规则库修订时，旧结果应失效；规则是编译对象（数据结构），可比较相等，符合论文所说的非嵌入 DSL 才能精确 self-tracking 的条件 [p.48]；若规则只是函数则只能悲观失效。因此将规则保持为数据并带版本，才能按规则粒度失效缓存。
- 迭代与固定点（层：固定顺序）：论文明确不处理环，若需要固定点需把迭代展开成有界步数的任务序列 [p.45]；引擎若把伪 flow 与抵免的相互作用改为固定点，论文不提供收敛保证，可参考 J2。
- 不适用：论文的收益（minimality、early cutoff）以"一次一次地增量重建、有持久存储"为场景；若引擎每次运行是独立批处理，则只有"一次运行内部的记忆化"（busy 加已处理键集合 [p.12]）和"候选之间共享"可用，跨运行的 traces 价值取决于是否真有多次运行。
