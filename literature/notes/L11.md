# L11 Lam, Oei, Shi, Marinov, Xie, 2019. iDFlakies: A Framework for Detecting and Partially Classifying Flaky Tests. ICST 2019, 312–322
版本：author（作者版，页脚为 IEEE 版权声明）；L11_Lam2019_iDFlakies_author.pdf；第 1–10 页全读（第 8 页 Table I 逐项数据略读），第 11 页参考文献略过

## 1. 问题与作者主张
- 作者指出回归测试希望失败可靠地指示被测代码有问题；不稳定测试对同一代码非确定性地通过或失败，使持续集成的信号不可靠，并侵蚀开发者对回归测试的信任 [p.1]。
- 作者把不稳定测试分成两类：只因运行顺序而不稳定的 order-dependent（OD）测试，和其余的 non-order-dependent（NOD）测试；OD 测试在给定顺序下可确定地通过或失败 [p.1]。
- 作者说研究的障碍之一是缺少当前真实项目中的不稳定测试数据集；以往工作或只研究旧版本，或只研究已修复的，或不区分 OD/NOD，或项目数很少 [p.1]。
- 作者的贡献：Maven 插件工具（检测并部分分类）、端到端框架 iDFlakies（Docker 化实验）、数据集（422 个不稳定测试）、以及一项研究 [p.1-2]。

## 2. 方法
- 工具以"轮"（round）为单位：一轮就是按某种配置把测试套件完整运行一遍；默认配置是 random-class-method，20 轮 [p.3]。
- 三步：设置步骤——在原始顺序下运行，要求每个测试 PASS 或 SKIP，最多重试用户指定次数（默认 3），仍有失败则丢弃该模块；运行步骤——按配置和轮数运行；分类步骤——对有失败的轮分类 [p.3]。
- 五种配置：original-order（反复按原顺序，任何失败直接判 NOD，不能发现 OD）；random-class（随机类顺序，类内方法顺序不变）；random-class-method（先随机类顺序再随机类内方法顺序，不跨类交错方法）；reverse-class；reverse-class-method（后两者只跑一次）[p.3-4]。
- 不跨类交错方法，理由是 JUnit 等常用框架不会产生那种顺序 [p.1-2]。
- 分类：测试在与原始顺序不同的"失败顺序"中失败时，重跑截至该测试的失败顺序（truncated failing order）与原始顺序（truncated original order）。若在失败顺序中再次失败且在原始顺序中通过，判 OD；否则判 NOD [p.3-4]。
- 复查：已分类的测试再次失败时，以一定百分比（实验用 20%）重新分类；判为 NOD 后永远不会改回 OD，而判为 OD 的可以改判为 NOD [p.3-4]。
- 框架：输入项目 URL 与提交，建 Docker 镜像（Ubuntu 16.04、Java 8、Maven 3.5.4），在容器内修改 pom.xml 加入插件并运行，最后把日志汇总到 SQL 数据库，日志含测试顺序、结果、堆栈等 [p.5]。
- 轮数可由轮数上限（Rounds）、总时间上限（Timeout）或两者取小（Both）决定；Timeout 下轮数为 ⌊Ttimeout/Toriginal⌋ [p.4-5]。

## 3. 数据与设置
- 项目：Maven + JUnit 的 Java 项目，来源有三：相关工作中的 44 个、GitHub 截至 2018 年 10 月最受欢迎的 150 个、2018 年 11 月内更新的最受欢迎的 500 个 [p.5]。
- 综合集（comprehensive）：183 个项目、2,921 个模块、1,880,362 个测试，跑全部五种配置；扩展集（extended）：500 个项目、2,250 个模块、93,722 个测试，只跑 random-class-method [p.6]。
- 683 个项目共 5,171 个模块，其中 945 个可被探索；另外 4,226 个不可：462 个无法构建，2,830 个没有声明 JUnit 或没有测试，476 个原始顺序三次都不全通过，458 个遇到工具限制 [p.6]。
- 每个项目最多 56 小时的时限 [p.2]。
- 评测指标：OD 与 NOD 数量；一轮含至少一个不稳定测试失败的概率（只在有不稳定测试的模块上，以观察到的轮数的比例计算）；各配置检出的不稳定测试数 [p.6-7]。

## 4. 结果
- RQ1：在 945 个模块里检出 422 个不稳定测试（来自 82 个项目的 111 个模块）：213 个（50.5%）判 OD，209 个（49.5%）判 NOD；38 个模块（31 个项目）含 OD，82 个模块（63 个项目）含 NOD [p.6]。作者对比 Luo 等人只含已修复测试的研究：其中 OD 占 12% [p.9-10]。
- RQ2：单个不稳定测试的失败概率从不足 1% 到超过 50% [p.6]。reverse-class-method 一轮出现不稳定失败的概率最高，总计 50.0%（OD 引起 46.8%，NOD 引起 5.3%）；只按 Maven 原始顺序运行的总概率 2.7% [p.7]。
- 作者解释：若一个 OD 测试被一个污染者测试破坏，均匀随机顺序下污染者排在它前面的概率是 50%；除 reverse-class-method 外其他配置的 OD 概率都远低于 50%，作者认为套件中有"清理者"测试常排在污染者与 OD 测试之间 [p.7]。
- RQ3：random-class-method 检出的唯一 OD 测试最多，162 个（占各配置检出 OD 测试合计的 88.0%）；reverse-class-method 检出 47 个（25.5%），其中 4 个 random-class-method 没检出，而后者检出 119 个前者没检出的 [p.7]。重排测试方法（而非仅重排类）有助于检出更多不稳定测试 [p.7]。
- 作者建议先跑一次 reverse-class-method 以快速检出一部分 OD 测试，再用 random-class-method 检出更多 [p.7]。
- NOD：多数配置发现 NOD 的概率相近；综合集 122 个 NOD 测试中，91 个靠分类步骤判为 NOD，其余 31 个由 original-order 配置直接判为 NOD [p.8]。对同时被 original-order 与 random-class-method 检出的 NOD 测试，两者检出概率的 Wilcoxon 符号秩检验在综合集 26 个测试上 p<0.05，在综合集加扩展集 33 个测试上不显著 [p.8]。
- 作者结论：原始顺序反复重跑不是检测不稳定测试的好配置——它不能发现 OD，对 NOD 也没有高出很多的检出概率；随机配置加分类步骤比重跑同一原始顺序检出更多 NOD（但随机配置轮数更多）[p.8-9]。
- 分类准确性：有 29 个测试起初被误判为 OD，后来改判为 NOD；209 个 NOD 中 125 个失败超过一次；原始顺序重跑在 7441 次分类运行中只有 3 次失败，作者因此建议只重跑失败顺序 [p.3-4]。
- 8/683 个项目已把 Surefire 的 runOrder 设为 random（只随机类顺序）；23 个被检出的 OD 测试位于带 @FixMethodOrder 注解的类中，其中 Activiti 项目的这类依赖后来被开发者修补并去掉注解 [p.9]。

## 5. 作者陈述的局限
- 工具和框架可能有缺陷，作者对汇总步骤的信心低于核心工具 [p.9]。
- 因随机顺序和测试本身的非确定性，精确结果可能难复现；作者记录了每轮的随机顺序以供重放 [p.9]。
- OD/NOD 分类可能出错：NOD 测试可能在分类重跑时再次因超时或网络而失败，被误判为 OD；工具基于观察到的运行分类，遇不到相关运行时可能把同时依赖顺序与其他因素的测试误判为 OD [p.3, p.9]。
- 实际不稳定测试数可能远高于报告值，NOD 可能漏得更多；只跑 mvn test 的单元测试，不含集成测试 [p.9-10]。
- 发现的泛化性有限：random-class-method 最好这一结论可能不适用于其他语言或不用 Maven/JUnit 的项目，GitHub 星数选出的项目未必有代表性 [p.10]。
- 工具不进一步分析 NOD 测试的原因，作者列为重要的未来工作 [p.9]。

## 6. 原文摘录
- "A desirable requirement for regression testing is that a test failure reliably indicates a problem in the code under test and not a false alarm from the test code or the testing infrastructure." [p.1]
- "Even if a test fails twice in the same order, it is no guarantee that the test is really OD, because other factors could have made an NOD test to fail twice." [p.3]
- "Our results suggest that simply rerunning tests in the original order where they pass is not a good conﬁguration for detecting ﬂaky tests" [p.8]
- "We attempt to mitigate this threat by logging the (random) orders in which our tool runs the tests so that others can reproduce the ﬂaky-test behavior by running the same orders." [p.9]
- "we strongly recommend developers to ﬁrst run the reverse-class- method conﬁguration once to quickly detect a portion of the OD tests and then use the random-class- method conﬁguration to detect more OD tests." [p.7]
- "The developer can run the tests in different orders after every change when tests are naturally rerun as part of the development process, and ﬂaky-test detection from our tool would effectively come “for free”." [p.9]

## 7. 对本库的可用点（笔记者推断）
- C 层"打乱顺序重跑"的具体配置：可借用论文的五种配置——原顺序重跑（只能发现非顺序因素）、倒序、随机、"先随机组再随机组内"的分层随机。本库的分组可对应"模块（法域/税种）→ 检查 → 案例"，分层随机不跨组交错，对应本库实际会出现的执行顺序（总控 `verify` 按模块执行）。§5 分级可定为：快级倒序一次；中级分层随机若干轮；全级更多轮。论文建议先倒序一次、再随机（p.7）。
- 论文发现原顺序重跑发现不了顺序依赖，对其他不稳定也不占优（p.8）。本库 C 层现有的"金标快照"按固定顺序比较，正是这种配置，不能替代打乱顺序检查。
- 记录随机顺序以便复现：论文把每轮顺序写入日志，别人可以重放（p.9）。对应 §5 结果格式：可在每条 `evidence` 或 `run` 元数据中记录本次的顺序种子与实际顺序，使失败可重放。
- 分类 OD 与 NOD 的方法可直接用于不稳定项的归因：失败后在"截至失败项的失败顺序"和"截至失败项的原始顺序"上重跑，若失败顺序再失败且原始顺序通过则为顺序依赖，否则为其他非确定性（p.3-4）。这比只报告"不稳定"更有用，可分别回应缓存-顺序缺陷（OD）与哈希种子（NOD）。论文自己也承认，两次都失败不能保证是 OD（p.3），所以本库在判为顺序依赖前宜再用多个随机顺序复核，或直接找出最小触发子序列。
- 论文的 SKIP/PASS 准入与"原顺序不过则丢弃模块"（p.3）：本库不稳定检查只应在基线全通过时运行；基线本身有失败时，应当先报失败，而不是把它归为不稳定。
- 对"污染者/清理者"的解释（p.7）：本库的缓存是典型污染者，各检查开头的重置是清理者。清理者存在会让随机顺序检出概率下降（论文观察到 OD 检出概率远低于 50%），因此"一次随机顺序没出错"不能说明没有依赖，需要多轮或系统化检查（见 L10 的依赖感知思路）。
- 不适用：论文是 Java/Maven/JUnit，对象是几十万测试的开源项目，工具靠自定义 JUnit 运行器；本库检查数少，运行一轮就是 `verify` 一次，成本结构不同。论文中的概率（如 2.7%、50.0%）依赖其数据集，不能迁移为本库的检出率预期。Docker 隔离的思路可对应"清空缓存与输出目录后新进程运行"，论文没有评估隔离的成本。
