# L10 Zhang, Jalali, Wuttke, Muşlu, Lam, Ernst, Notkin, 2014. Empirically Revisiting the Test Independence Assumption. ISSTA 2014, 385–396
版本：author（作者版）；L10_Zhang2014_TestIndependence_author.pdf；第 1–10 页全读，第 11–12 页参考文献略过

## 1. 问题与作者主张
- 作者指出测试集中各测试应当相互独立：任一测试不影响其他测试的结果，任何顺序运行结果相同；测试优先排序、选择等技术都以此为前提，但这一前提很少被质疑或提及 [p.1]。
- 作者统计 2000 至 2013 年发表的 31 篇测试优先排序论文：27 篇明示或默示假定测试独立，3 篇承认依赖可能影响结果，仅 1 篇在算法设计中考虑了测试依赖 [p.1]。
- 作者报告五项结果：对真实依赖测试的研究；测试依赖的形式化与"检测依赖测试是 NP 完全"的证明；四种检测算法；在 4 个真实程序上的检测结果；依赖测试对五种测试优先排序技术的影响 [p.1-2]。
- 作者认为测试依赖导致假阳性和假阴性结果，不应再被忽略 [p.2]。

## 2. 方法
- 实证研究：在 Apache、Eclipse、JBoss、Hibernate、Codehaus 五个缺陷跟踪系统里搜四个短语（"dependent test"、"test dependence"、"test execution order"、"different test outcome"），人工检查前 450 条匹配，每个候选至少两人检查；排除描述含糊的报告，也排除结果受非确定性（如多线程）影响的测试 [p.2-3]。
- 形式化：环境 E 含全局变量、文件、操作系统服务等；测试执行是 exec: T×E→E；测试结果 R(t|E) 为 PASS 或 FAIL；测试集是有序序列 [p.5]。
- 定义 6（显式顺序依赖测试）：存在测试集 T 的两个排列 S1、S2，使 R(S1|E0)[t] ≠ R(S2|E0)[t]；以默认顺序的结果作期望结果。作者不把仅影响内部状态（如哈希表元素顺序）而不影响测试结果的情形算作依赖 [p.1, p.5]。
- 定理 1：判定某测试是否为依赖测试的问题 NP 完全（由精确覆盖问题归约），证明因篇幅略去，见文献 [69] [p.5]。形式化不考虑非确定性测试、不终止的测试，也排除自依赖（同一测试执行两次结果不同）[p.5]。
- 四种检测算法，共用同一基础流程：先按默认顺序跑得期望结果，再按算法给出的若干顺序运行，结果不同的测试判为依赖 [p.5-6]。
  - 反转：把测试集倒序运行一次 [p.5-6]。
  - 随机：重复多次随机打乱顺序运行（实验取 10、100、1000 次）[p.6]。
  - 穷举有界：执行所有长度为 k 的排列（实验取 k=1 与 k=2），排列数降为 O(n^k) [p.6]。
  - 依赖感知有界：在隔离运行中记录每个测试读写的静态字段与文件，只运行存在"先前测试写、后续测试读"关系的排列，其余排列可安全丢弃 [p.6-7]。
- 四种算法都是"可靠但不完备"：找到的依赖测试都是真的，但不保证找全（除非界限取到 n）[p.2, p.5]。
- 工具 DTDetector：每次排列在新 JVM 中运行，运行后删除临时文件；两次结果相同的标准是都通过，或抛出同一异常/断言失败且来自同一行代码；用 ASM 插桩静态字段访问，用 SecurityManager 记录文件访问；可手工指定"无依赖字段"（如日志计数）[p.6-7]。

## 3. 数据与设置
- 实证研究：从前 450 条匹配的报告中得 53 条与测试依赖有关，共 96 个依赖测试（Apache 26、Eclipse 59、JBoss 6、Hibernate 3、Codehaus 2）[p.3]。
- 评测程序（Table 3，人工写的单元测试数）：Joda-Time 27,183 行、3,875 个；XML Security 18,302 行、108 个；Crystal 4,676 行、75 个；Synoptic 28,872 行、118 个。另用 Randoop 为每个程序生成 5,000 个测试，去冗余后：XML Security 665、Crystal 3,198、Synoptic 2,467；Joda-Time 的自动生成套件因依赖当前时间、非确定而弃用 [p.7]。
- 评测五种优先排序技术 T1、T3、T4、T5、T7（随机排序，及按语句、方法等覆盖优先），取自文献 [20] 所列技术中不需要故障历史的五种（其余 9 种因缺故障历史未实现） [p.8]。
- 手工提供 39 个"无依赖字段"，约 30 分钟；每个输出的依赖测试都人工确认不是非确定性所致 [p.7]。
- 环境：2.67GHz Intel Core、4GB 内存（JVM 分得 2GB）、Windows 7 [p.7]。

## 4. 结果
- 暴露所需测试数（Table 1）：单独运行即暴露 6 个，需 2 个测试 73 个，需 3 个测试 2 个，自依赖 1 个，信息不明 14 个；作者称至少 82% 可由不超过 2 个测试暴露 [p.3]。
- 根因：59（61%）来自对共享静态变量的副作用访问，10（10%）来自数据库，4（4%）来自文件系统，其余 23（25%）不明 [p.3-4]。
- 后果：94/96 导致假警报，2/96 造成漏报（掩盖缺陷）[p.3]。Eclipse SWT 的一份缺陷报告，49 个测试在先跑别的测试时失败，开发者调查一个多月才发现是未写明的测试依赖 [p.2, p.4]。Apache CLI 的一个缺陷被两个依赖测试掩盖超过 3 年（2004 年 3 月报告，2007 年 3 月解决）[p.2, p.4]。
- 开发者处置：96 个中开发者认为 94 个（98%）是主要或次要问题；仅 38（40%）被修复，49（51%）靠在测试代码里加注释记录依赖，9（9%）未处理；38 个修复中 6 个（16%）改的是程序代码、32 个改的是测试代码，后者里 28 个（87%）是在脚本或配置文件里手工指定测试执行顺序，3 个删除，1 个合并 [p.3]。
- 没有一个研究中的依赖测试能靠默认顺序运行发现；每个都是在顺序被改变（用户意外改变或工具改变）时才报告 [p.4]。
- 检测：DTDetector 在人工写的测试中找到 29 个依赖测试（其中 27 个此前未知），自动生成的测试中 1,311 个 [p.7-8]。自动生成测试中依赖比例 20%，人工写的 0.7% [p.8]。所有被检出依赖测试的根因都是对静态字段的不当访问 [p.8]。
- 人工写的测试集上各算法检出数合计（Table 4）：反转 21；随机 10/100/1000 次分别 21/24/29；穷举 k=1 为 23，k=2 为 ≥24（未跑完）；依赖感知 k=1 为 23，k=2 为 ≥25（未跑完）[p.8]。
- 作者称随机算法（1000 次）找到其他算法发现的全部依赖测试，另外多发现 Joda-Time 的 4 个，这 4 个只在三个测试以特定非默认顺序运行时显现；穷举与依赖感知算法在 Joda-Time 上无法扩展到 k=3 [p.8]。依赖感知算法在 XML Security 自动生成套件中比穷举少找一个，原因是未跟踪动态加载类的静态字段访问 [p.8]。
- 耗时：随机 1000 次在 Joda-Time 人工套件（3875 个测试）约 1.5 小时；该套件的 k=2 有 15,011,750 个长度为 2 的排列，估计约 58 天；依赖感知 k=2 比穷举 k=2 快约一个数量级；每个测试单独新开 JVM 比反转慢 10–138 倍 [p.8, p.10]。
- 对优先排序的影响（Table 6）：在人工写的套件上，依赖测试使五种技术都出现与默认顺序不一致的测试，合计 T1 12、T3 11、T4 17、T5 11、T7 12，主要来自 Crystal；XML Security 与 Synoptic 为 0，Joda-Time 仅 T4 为 1 [p.9]。
- 开发者反应：Joda-Time 开发者确认其余新发现，认为是库内非预期的交互；Crystal 开发者确认全部为非预期并开了缺陷报告；SIR 维护者接受了修复补丁，称测试应"stand alone"，是"test engineering 101" [p.9]。
- 作者的四项结论：依赖测试在人工与自动生成的测试集中都存在；它们反映测试集的弱点而不是被测代码的缺陷；会干扰优先排序；随机算法检测最有效 [p.9]。

## 5. 作者陈述的局限
- 实证研究只覆盖 Java 与 JUnit；采信开发者对哪些测试依赖、严重程度和所需测试数的判断；搜索词不同可能发现更多 [p.4]。
- 评测只用 4 个开源程序（是最先尝试的 4 个）；只考察单元测试之间的显式依赖，集成或系统测试若各自独立环境可能依赖较少；因问题复杂度，没有 DTDetector 的召回数据；只评估五种优先排序技术 [p.9]。
- 形式化排除非确定性测试和自依赖 [p.5]。
- 算法可靠不完备；穷举算法在较大套件上因排列数过多而不可行 [p.5, p.8]。

## 6. 原文摘录
- "In a test suite, all the test cases should be independent: no test should aﬀect any other test’s result, and running the tests in any order should produce the same test results." [p.1]
- "A dependent test manifests when another test alters the execution environment in a way that invalidates those assumptions." [p.2]
- "None of the dependent tests we studied can be identiﬁed by running the existing test suite in the default order." [p.4]
- "Dependent test detection techniques can bound the search space to a small number of tests." [p.4]
- "Non-determinism does not imply dependence" [p.10]
- "Determinism does not imply independence: a program may have no sources of nonde-terminism, but two of its tests can be dependent." [p.10]
- "The randomized algorithm is surprisingly eﬀective in detecting dependent tests." [p.8]

## 7. 对本库的可用点（笔记者推断）
- C 层"打乱顺序重跑"的定义依据：论文定义 6（存在两个排列使某测试结果不同）可直接作为本库"顺序不稳定"的判据——以默认顺序为期望，任何排列下结果（`status` 与 `measured`）不同即不稳定，对应 §2 C 层与 §4 门禁"不稳定项数大于 0 阻断"。2026-10-09 的缓存-顺序缺陷正是论文所述的"先跑的测试初始化了全局状态，掩盖后跑测试的缺陷"（CLI 例子，p.4）。
- 算法选择：论文中随机打乱（1000 次）比反转与有界穷举都有效，且唯一找到需要 3 个测试的依赖 [p.8]；反转最便宜。本库可在"快"级别做一次反转加少量随机排列，"全"级别做更多次随机；穷举 k=2 的成本（Joda-Time 估计约 58 天）说明不宜做穷举，但本库的检查数目远少于 3,875，k=2 是否可行要按实际检查数估算，论文没有给出这个数。
- "依赖感知"思路可借用：记录每个检查读写了哪些全局状态（模块级缓存、`official/` 文件、`out/` 文件），只对共享状态的检查对做排列 [p.6-7]。注意论文的做法依赖插桩，本库需自己实现；也要像论文那样把"读也算写"当保守处理，且被动态加载的状态会漏检（论文漏过一个，p.8）。
- 隔离运行作为基线：每个检查单独在新进程里运行，与整体运行比较（k=1）[p.6]。对应 §5 的运行分级：此检查开销大（论文称 10–138 倍），宜放在"全"级。
- 结果比较标准：论文把"都通过，或抛出同一异常且位于同一行"视为结果相同 [p.7]。对应 §5 结果格式：比较时应比较 `status` 加失败的 `check_id` 与 `subject`，而非仅通过与否，避免失败原因变了却被当作一致。
- 需要区分"顺序依赖"与"非确定性"：作者明确两者互不蕴含 [p.10]，且形式化排除了非确定性。本库的两项不稳定检查（顺序、哈希种子）对应两种不同病因，报告时宜分别标注，不能合并为一个计数。
- 论文 §2.2 说默认顺序的结果是"期望结果"，而默认顺序本身也可能掩盖缺陷（漏报）。本库金标快照（C 层）是按固定顺序生成的，故快照不能证明其对顺序不敏感，需同时做打乱检查。
- 不适用：论文面向 Java 单元测试和静态字段，本库是 Python 管线和数据文件；论文给出的比例（61% 来自静态变量等）不能迁移；NP 完全结果只针对"判定任意套件"，对本库检查数很少的场景无直接意义。
