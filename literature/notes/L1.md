# L1 McKeeman, 1998. Differential Testing for Software. Digital Technical Journal 10(1), 100–107
版本：published（出版商存档页的网络档案副本）；L1_McKeeman1998_DifferentialTesting.pdf；第 1–8 页全读（第 8 页为致谢与参考文献，略读）

## 1. 问题与作者主张
- 作者指出测试中最难的问题是评估测试结果：回归测试只能检查结果未变，除非结果已知正确才有意义；对随机生成的测试，事先知道期望结果不现实 [p.2]。
- 作者主张差分测试（differential testing）提供部分解决办法：把同一测试喂给多个可比较的程序，若有一个给出不同结果，就可能暴露了缺陷；用大量计算周期代替人工设计与评估测试 [p.2]。
- 作者主张它是随机测试的一种，与基于商业测试集和本地测试的回归测试互补，能发现否则不会被发现的缺陷，成本低、适用范围广，但在被测软件的开发者中不受欢迎 [p.1, p.7]。
- 作者认为测试输入的质量决定能否触及被测程序深层逻辑，并给出由低到高的七级输入质量 [p.3]。

## 2. 方法
- 差分流程：一个 test master 生成测试并分发到多个 test bed，各自运行后由 test analyzer 比较输出；被测编译器崩溃或死循环、部分运行异常、全部正常但输出不同，分别写入 crash、loop、abend、diff 目录；比较用编译器崩溃或死循环时丢弃该测试，因为报告比较对象的缺陷不是测试目标 [p.5-6]。
- 输入七级：ASCII 字符序列；词、分隔符与空白；语法正确的 C 程序；类型正确；静态符合标准；动态符合标准；符合模型（从已部分生成的模型程序出发）[p.3]。
- 生成方法：随机文法（stochastic grammar），每条文法规则配概率；同一非终结符的概率之和为 1.0，递归规则要偏向非递归备选以免生成器失控；可解线性方程组得各非终结符的期望串长 [p.3-4]。
- 误报控制：C 标准中未指定、未定义或由实现定义的结构允许不同结果；第 6 级对每个发现的差异重新生成同一测试，把每个算术运算换成带标准违反检查的函数调用，若断言触发则丢弃该测试；第 7 级通过模型程序控制输出，并把舍入误差引起的差异排除（浮点数只打印几位有效数字）[p.2, p.4-5]。
- 测试缩减：对被归档的测试反复施用 23 种启发式变换（删语句、删声明、把常量改成 1、把标识符改成 1、删一对花括号、删 if 子句等），仍能触发同一现象就保留，直到整轮不再改变 [p.6-7]。
- 分发：用共享文件系统与定时查看的 watcher 程序同步 [p.5-6]。

## 3. 数据与设置
- 经验报告，没有受控实验或数据集。对象是 DIGITAL（后来 Compaq）的 C 编译器与运行时系统；生成器最初用 Tcl 写成，作者称 Tcl 在第 4 级之后已接近其作为实现语言的极限 [p.1, p.4]。
- 指标：文中未给出统一的评测指标；质量度量仅作为用法提出（每百万次运行失败的测试数）[p.7]。

## 4. 结果
- 表 1 列出短文本即可触发的缺陷，例如 if (1.1) 常量浮点表达式判为假、1==1==1 的虚假语法错误、1E1000 使编译器崩溃、1 >> INT_MAX 的二十分钟编译时间、x != 0 ? x/x : 1 的错误答案；括号嵌套 10 层为虚假诊断，100 层为编译器崩溃，10,000 层为服务器崩溃 [p.6]。
- 第 1 级输入很少能执行到词法分析器与其诊断之外的代码；第 2 级发现的缺陷包括某编译器不能处理前导零过多的 0x000001 [p.3]。
- 第 5 级生成的程序有很大比例因除零而异常终止；作者通过降低除法、布尔值及其作除数的概率来减少这类浪费 [p.4]。
- 测试缩减典型地把 500–600 行的生成程序缩到几行，缩减过程一般要 10,000 次以上编译操作 [p.7]。
- 该技术在 DIGITAL 每天暴露新的 C 编译器缺陷；多数缺陷在比较用编译器中，但也有相当数量在 DIGITAL 自己的代码中并被修复 [p.7]。
- 作者未报告缺陷总数、误报率或各级输入的缺陷发现比例。

## 5. 作者陈述的局限
- 差分测试最适用于质量已受控、已知未解决错误很少的软件；有大量积压缺陷的团队不愿再增加机器人发现的缺陷 [p.2]。
- 开发者常反对：认为随机测试发现的不是会困扰客户的错误；Hoare 的评语是不能一个个修无限多的缺陷 [p.2]。
- 差异不一定是缺陷：未指定行为与诊断格式使跨系统比较困难（误报）[p.2]。
- 随机文本只提供对编译器逻辑的浅层覆盖 [p.2]。
- 分发方案不抗崩溃与死循环，也不易启动，且不快 [p.6]。
- 一个缺陷未修复前会被反复发现，需要人工丢弃重复和不感兴趣的测试 [p.7]。
- 用多数规则度量质量时，作者写道失败方的作者可以修复缺陷或证明多数是错的 [p.7]。

## 6. 原文摘录
- "The ugliest problem in testing is evaluating the result of a test." [p.2]
- "If a single test is fed to several comparable programs (for example, several C compilers), and one program gives a different result, a bug may have been exposed." [p.2]
- "The trade-off is to use many computer cycles instead of human effort to design and evaluate tests." [p.2]
- "The results of two tested programs may differ and yet still be correct, depending on the requirements." [p.2]
- "Differential testing is most easily applicable to software whose quality is already under control, that is, software for which there are few known outstanding errors." [p.2]
- "Supposing that the majority rules, a million tests can be run on a set of competing compilers." [p.7]

## 7. 对本库的可用点（笔记者推断）
- §3.3 独立核验器对“法定税率乘全额”的完全独立重算，就是差分测试的最小形式：两个实现、同一输入、比较输出。论文支持“差异即候选缺陷、人只看差异”的流程 [p.2]，对应核验器与引擎结果不一致时作阻断项。
- 论文的前提是两个实现“可比较”且彼此独立。本库的独立重算若读同一参数表、同一日期有效性函数，则参数表错误会在两边同时出现，差分抓不到；论文没有讨论共因错误，这是推断。参数表本身仍要靠 A 层与官方标签核对。
- 论文承认差异不等于缺陷（未指定行为）[p.2]。对应本库：两个实现的差异可能来自口径（D 系列）而非错误，比如是否含税基数、取整顺序；核验器的比较需要预先约定舍入与取整，否则全是误报。论文处理舍入的办法是只比较前几位有效数字 [p.5]，税额计算不能这样做，应改为约定到分的取整规则。
- §8b 公司自算税额作对照物：论文给出“旧实现退役时新实现须复现旧行为，并标出所有与旧结果不一致的新结果（无论对错）”[p.7]，与把公司自算税额当对照物、不一致处逐条查原因的做法一致；但公司自算不是正确答案，不一致可能是对照物自己的错，论文也说比较对象自身的缺陷不是测试目标 [p.6]。
- §3.2 与 C 层：论文把崩溃作为无需预言的一类结果 [p.2]，对应本库不变式（崩溃、异常、负税额）。第 7 节“用测试缩减把 500 行缩到几行”[p.7] 与 C 层 delta debugging 同类：电池案例触发失败时，自动缩小案例再交给人看。
- 论文的多数投票度量质量 [p.7] 不适用：税务引擎只有一个，且官方文本才是标准（§0 原则），不能用多个实现的多数代替官方答案。
- 论文的第 7 级“把现场缺陷推广成一类相近测试”[p.5] 可用于：每个出现的缺陷案例，生成邻近变体（改金额、改日期、改门槛两侧）一并纳入电池。
