# J12 Goldstein, Cutler, Dickstein, Pierce & Head, 2024. Property-Based Testing in Practice. ICSE 2024（Lisbon）
版本：author（作者版）；J12 文件为作者自存 PDF；第 1–11 页全读（正文，含 Lessons Learned 与 Related Work），第 12 页起参考文献略过

## 1. 问题与作者主张
- 作者指出 property-based testing（PBT）让用户写可执行的形式化规格，由自动化框架在大量自动生成的输入上检查；随着 PBT 的使用范围扩大，需要理解开发者在实践中如何使用、认为强弱何在 [p.1]。
- 两个研究问题：RQ1 成功且成熟的 PBT 文化有何特征；RQ2 是否存在由真实开发者需求引出的未来研究机会 [p.1]。
- 作者基于对 Jane Street 的 30 次深度访谈主张：PBT 的主要强项在测试复杂代码并提高超出常规测试的信心，多数用法落在少数"高杠杆"（high-leverage）用法上；主要弱项在写 property 和随机数据生成器的复杂性，以及难以评估测试的有效性 [p.1]。
- 作者主张开发者主要把 PBT 用于复杂系统的组件，期望它比示例式单元测试更有信心且跑得快；property 还起到"持久文档"的次要作用 [p.1]。

## 2. 方法
- 半结构化一小时访谈；测试者的提示涵盖：测试了哪类 property、如何生成输入、如何评价测试有效性、如何缩小（shrink）失败输入；维护者另有脚本 [p.3]。
- 访谈由自动转写服务转写，用 thematic analysis 做 open coding 与 axial coding [p.3-4]。
- 作者说明未按"饱和"（saturation）为止的标准访谈，只是在接近结束时觉得不再学到新内容 [p.3]。
- 术语：property 是可执行规格；generator 产生随机输入；shrinker 把大的失败输入缩小；precondition 定义输入是否有效 [p.2]。

## 3. 数据与设置
- 对象：Jane Street（金融科技公司），主要使用 OCaml 与 Core QuickCheck；招募 31 位参与者，进行 30 次访谈（一次联合访谈）；26 位测试者（testers）、4 位维护者（maintainers）；跨 15 个团队，覆盖 Trading（2/30）、Trading Infrastructure（13/30）、Quantitative Research（5/30）、Developer Infrastructure（11/30）[p.2-3]。
- 回答问卷者的软件工程经验为 1 至 26 年（中位数 7），使用 PBT 1 至 20 年（中位数 6），舒适度中位数 6/7 [p.3]。
- 对照的测试方式：Jane Street 最常用的是示例式 "expect tests"，另有 AFL 与 AFL++ 模糊测试 [p.5]。
- 作者回报的是计数（如 17/30），并强调这些来自访谈，不是度量 [p.4-7]。

## 4. 结果
- 好处：10/30 提到 PBT 擅长探索边缘情形；9/30 明确说增加了对代码正确的"信心"；10/30 说 property 测试找到了其他方法未发现的缺陷 [p.4]。12/30 将 property 用作文档与沟通，18/30 提到在代码评审中 property 是表达程序行为的紧凑方式 [p.4]。
- 与其他测试的比较：没有一方普遍占优；示例式测试简单时轻量，代码难写对或写例子乏味时 PBT 更合适 [p.5]。PBT 几乎总在构建系统中运行，时间预算严格，从"30 秒"低至"50 毫秒"，以免触发每个库一分钟的单元测试超时；模糊测试则跑在"带外"，时间尺度为小时或天，有人把一个模糊测试在备用服务器上忘了跑了一年半 [p.5]。
- 写规格：16/30 说写规格拖慢进度；P4 称"最常见的失败模式是根本不知道该测什么 property" [p.5]。可变状态与外部环境交互使 property 更难写 [p.5]。
- 高杠杆场景（作者称开发者先看到现成的可测 property 再决定用 PBT）：differential properties（对照参考实现或抽象模型）17/30，为最常见；classical properties 11/30；round-trip properties 11/30；catastrophic failure properties 7/30 [p.6]。作者称其共同点是存在简洁抽象，引用 P9 的话："最有用的情形是有一个很好的抽象配上复杂的实现" [p.6]。
- 生成数据：17/30 需要生成满足 precondition 的值（有效邮政地址、结构良好的 XML、红黑树等很难随机得到）；5/30 想要"真实"分布的数据；19/30 用手写生成器，19/30 用按类型推导的生成器；手写生成器被认为"乏味"（6/30）或"高投入"（7/30）[p.6]。一位参与者指出"想要覆盖一切"与"想要对多数输入真实"之间有张力 [p.6]。
- 理解失败：随机生成器常给出太大的失败样例；一位参与者称 shrinking "必要"，两位自制 PBT 框架者称其为最重要的功能之一；参与者讨厌手写 shrinker，且手写 shrinker 容易不小心破坏不变量（P13）[p.7]。参与者还想看 shrinking 过程中的中间值 [p.7]。
- 理解成功：作者称 11 位（超过三分之一）承认没有像应当的那样思考测试有效性，其中 3 位见到 property 抓到几个缺陷就不再改进，其余信任库自带或推导出的生成器；P19 回忆一次已发布代码中的缺陷，因为生成器"没有生成我心里想的那种情形"而漏测，P14 称"不知道它在生成什么" [p.7]。
- 验证 PBT 测试的做法：Mutation Testing 7/30（故意在代码里加缺陷，看测试能否找到）；Example Inspection 8/30（看一批生成样例）；Code Coverage 2/30；Property Coverage 1/30（度量 property 本身的覆盖，作者称较弱因为对被测系统无说明，但易于获得）；另有 2/30 用示例式测试补充 [p.7]。
- 参与者要求提高"可见性"（visibility，P16）与"可检视性"（inspectability，P30），如生成输入的可视化、生成列表的平均长度等统计、代码覆盖 [p.8]。
- 六条观察 OB1–OB6：PBT 用于对复杂系统建立信心；property 用作沟通规格的工具；PBT 需要快；PBT 在高杠杆场景中被机会性使用；开发者把写生成器视为干扰，更偏好推导；开发者可能不去追问没发现缺陷的 property [p.8-9]。
- 研究机会 RO1–RO7，含 RO5：改进 shrinking 的界面，建议框架引入 internal test-case reduction（作者引用 [36, 52]），其附带好处是总产生有效值；作者举例，若 shrinker 输出元组 (0, 0)，会误以为任何整数元组都触发缺陷，而实际可能要求第一个分量恰为 0，所以最小的失败样例不一定最有帮助 [p.10]。RO6：工具应总是公布被丢弃用例（未通过 precondition）的计数 [p.10]。

## 5. 作者陈述的局限
- 参与者多半使用同一套工具链、语言与生态（OCaml、Jane Street），结果可能低估其他环境的用法与挑战 [p.4]。
- 参与者多为有经验、对 PBT 舒适的开发者，对新手的体验报告不足 [p.4]。
- 没有按饱和度访谈，更多访谈可能有新发现 [p.4]。
- 访谈研究的固有局限：参与者可能记不准经历；访谈者本身是 PBT 研究者，对结果有利益关系，可能无意中突出了对 PBT 有利的结果 [p.4]。
- 找到的对 PBT 持批评态度的参与者只有两位（P19 与 P20），且其批评也是建设性建议 [p.3-4]。

## 6. 原文摘录
- "automated tools for generating test inputs risk giving developers a false sense of security." [p.9]
- "11 of them—more than a third—said they did not think as hard as they should about testing effectiveness" [p.7]
- "I think the most common failure mode is actually not knowing what properties to test." [p.5]
- "It’s easy to write a shrinker that accidentally does not preserve some invariant, and that makes your test fail." [p.7]
- "tools should always announce counts of discarded test cases" [p.10]
- "the smallest failing example is not the most helpful one" [p.10]

## 7. 对本库的可用点（笔记者推断）
- 测试充分性不止是不变量（电池层）：访谈中 11/30 的开发者承认没有追问测试有效性，其中有人见到 property 抓到几个缺陷就停止改进 [p.7]；OB6 指出通过的 property 也可能只是输入没有触发潜在缺陷 [p.9]。这与本库的"自测环路驱动到零缺陷"相似：电池全通过不说明规则正确。可对应的做法是引入作者列出的验证手段——mutation testing（7/30 使用）、示例检视（8/30）、覆盖（2/30）[p.7]——并把它们列为电池的必选输出，而不是可选项。
- 生成器分布透明（电池层）：作者建议工具总是报告被丢弃用例数 [p.10]，并提供生成分布的统计 [p.8]。本库应对每个事实包、模板、辖区、时点的取值输出直方图，特别是"阈值邻域内的用例占比"、"被约束过滤掉的组合数"，使"阈值邻域从未被检验"成为可见的数字，而不是靠人想到。
- Precondition 与有效性：参与者需要满足 precondition 的值（17/30），filter 式生成会浪费大量用例 [p.2, p.6]。本库的合法事实组合（例如某辖区无某税种、持股比例范围）应直接构造生成而非生成后过滤，并报告过滤率；这与 J8 的约束覆盖数组呼应。
- 高杠杆 property 的可用类型：differential/model-based（17/30）[p.6] 可对应为"同一事实用两种独立路径算税并比较"，例如引擎结果与官方样例、条款中的算例、或另一独立实现（如对简单情形的手算公式）比较；round-trip 可对应"税后金额还原"，以及"缩放金额 k 倍则上下界缩放 k 倍"这类已有 metamorphic 关系。作者称这些类型的共同点是存在简洁抽象 [p.6]，而本库可检验的 property 取决于哪些规则有这样的简洁对照；对没有对照的规则（如复杂的联合申报规则）作者的数据只说明开发者也会避开 [p.9]。
- Catastrophic failure properties（崩溃、断言）只是弱 oracle，作者称这些提供的对代码质量的信心较少 [p.6]。本库的现有不变量（floor ≤ ceiling、非负、每个税项有引文）属于这一档，不应据此宣称正确。
- Shrinking（电池层）：参与者要求自动化缩减、更多中间样例，作者建议采用 internal test-case reduction，因为总是产生有效值 [p.7, p.10]（详见 J7）。作者还提醒最小失败样例不一定最有帮助，例如 (0, 0) 会掩盖"仅当第一分量恰为 0 时失败"[p.10]。对本库：失败报告应同时给出最小例与"边界两侧的对照例"，而不是只给最小例。
- 指标作弊：作者没有讨论人为放宽阈值或把规则宣告"silent"；其访谈显示的行为模式是"见到 property 抓到几个缺陷就觉得足够" [p.7]，可作为风险旁证，但这是类比，不是论文对指标作弊的结论。
- 属性即文档：12/30 把 property 当持久文档 [p.4]。本库的不变量与对照算例可以链接到库的 cite_id，成为"规则的可执行规格"，在重建时随库一起跑（层：官方库与电池的衔接）。
- 速度预算：PBT 被要求在 50 毫秒到 30 秒内跑完 [p.5]。本库电池约 300 个用例是批处理，不受此约束；但若加入组合覆盖与变异测试，应分层：快速集每次改动都跑，完整集在重建时跑。
- 不适用：研究是 OCaml 与金融科技工程师的访谈，数据是计数而非效果度量，没有任何关于测试发现缺陷比例的定量结论；也没有讨论数据库或规则库的质量检查，更没有法条正确性的 oracle。论文不能说明 PBT 是否会在税法规则上找到更多缺陷。
