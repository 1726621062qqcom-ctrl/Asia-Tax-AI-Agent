# I13 Han et al., 2026. RAG vs. GraphRAG: A Systematic Evaluation and Key Insights. KDD 2026（预印本 arXiv:2502.11371v3）
版本：preprint；I13_Han2026_RAGvsGraphRAG_preprint.pdf；第 1–8 页全读，附录 G、L、M 略读，其余附录与参考文献略过

## 1. 问题与作者主张
- 作者指出现有面向文本的 GraphRAG 研究多在各自任务、数据集、建图启发式与评测协议下进行，难以判断显式图结构何时有帮助、何时有害，也掩盖了建图成本、检索延迟与存储开销 [p.1]。
- 作者主张 RAG 与 GraphRAG 表现互补而非存在一致的优胜者：RAG 在单跳、细节型事实查询上更好，GraphRAG 在多跳、推理型问题上更有效 [p.2]。
- 作者主张 GraphRAG 的设计选择影响大（如 community-based global search 会牺牲查询细节），评测协议也会改变结论（LLM-as-a-Judge 对摘要呈现顺序敏感）[p.2]。
- 作者主张 GraphRAG 往往带来更高的建图成本、检索延迟与存储，其表现对建图质量敏感 [p.2]。
- 作者研究 Selection（按查询类型路由）与 Integration（合并两种证据）两种混合策略 [p.2]。

## 2. 方法
- RAG：稠密检索，文档切成约 256 token 的块，用 text-embedding-ada-002 嵌入，top-k 检索，默认 k = 10 [p.3]。
- GraphRAG 四类：KG-based（LlamaIndex，两个变体：仅三元组、三元组+原文）；Community-based（Edge et al.，Local 与 Global 两种检索）；Text-centric graph-guided（HippoRAG2：实体链接图引导取回原文块）；Hierarchical summary-based（RAPTOR）[p.3]。
- 统一设置：建图用 GPT-4o-mini（GPT-4o 的结果在附录）；可选 cross-encoder reranker（BAAI/bge-reranker-large）；可选 iterative retrieval（IRCoT）；生成器为 Llama-3.1-8B-Instruct 与 70B；检索结果先保存，再由统一脚本生成 [p.3]。
- Selection：用 LLM 的 in-context learning 把查询分为 fact-based 或 reasoning-based，再分派给 RAG 或 GraphRAG（Community-GraphRAG Local）；Integration：两者并行检索后把上下文拼接送入生成器 [p.5]。

## 3. 数据与设置
- QA 数据集：Natural Questions（单跳）、HotPotQA 与 MultiHop-RAG（多跳；后者含 Inference、Comparison、Temporal、Null 四类查询）、NovelQA（21 类查询）；NQ 与 HotPotQA 用 P/R/F1，MultiHop-RAG 与 NovelQA 用 accuracy [p.3-4]。
- 摘要数据集：SQuALITY、QMSum（单文档），ODSum-story、ODSum-meeting（多文档）；指标 ROUGE-2 与 BERTScore；另用 LLM-as-a-Judge 比较 Comprehensiveness 与 Diversity [p.7]。
- 主文报告 Llama-3.1-8B 的结果，70B 结果在附录 [p.4]。

## 4. 结果
- Table 1（NQ / HotPotQA，F1 %）：RAG 64.78 / 60.04；RaptorRAG 60.04 / 61.31；KG-GraphRAG（仅三元组）34.28 / 25.02；KG-GraphRAG（三元组+原文）50.27 / 42.60；Community Local 63.01 / 61.66；Community Global 54.48 / 45.16；HippoRAG2 61.03 / 63.01 [p.4]。
- Table 2（MultiHop-RAG，Overall accuracy %）：RAG 67.02；RaptorRAG 68.78；KG（仅三元组）41.24；KG（三元组+原文）48.51；Community Local 69.01；Community Global 64.40；HippoRAG2 70.27。分类型：Temporal 上 RAG 30.70，Community Global 53.34，Community Local 50.60；Null 上 RAG 96.01，Community Global 19.27 [p.4]。
- 作者称 KG-based GraphRAG 一般表现较差，原因是图覆盖有限：HotPotQA 中约 65.8%、NQ 中 65.5% 的答案实体出现在构建的 KG 中（附录 C）[p.4]。
- Reranking 与 IRCoT 对 RAG 和 GraphRAG 一般都有提升，在 MultiHop-RAG 上增益更大；RAG 在单跳细节问题上仍占优；Community-GraphRAG（Local）加 IRCoT 后在 Null 查询上明显偏低 [p.4]。
- 混淆矩阵（Llama 3.1-8B）：MultiHop-RAG 上仅 GraphRAG 答对 13.6%，仅 RAG 答对 11.6%，两者皆对 55.4%，两者皆错 19.4%；NQ 上两者皆对 47.2%，仅 RAG 对 7.8%，仅 GraphRAG 对 6.0%，两者皆错 39.0% [p.5]。
- Selection 与 Integration 在各数据集上一般提升 QA 表现；MultiHop-RAG、Llama 3.1-70B 上分别比最佳基线高 1.1% 与 6.4%；Integration 一般高于 Selection，但需每个查询运行两套系统，成本更高 [p.5-6]。
- Table 4（MultiHop-RAG）：构建时间 RAG 135 s、KG-GraphRAG 7702 s、Community-GraphRAG 5560 s；检索时间 1724 s、14434 s、1249 s；存储 127MB、117MB、165MB [p.6]。
- Table 5（70B，MultiHop-RAG Overall）：无图 65.77，GPT-4o-mini 建图 71.17，GPT-4o 建图 75.08；Temporal 类 25.73 / 49.06 / 58.49。作者称更强的建图模型一致提升表现，但成本更高 [p.6]。
- 摘要任务：作者称 RAG、RaptorRAG、HippoRAG2 一般表现好，因为取回原文块；Community Global 弱于 Local；Integration 常与单独 RAG 相当（QMSum ROUGE-2 F1：RAG 6.32，Integration 6.34）[p.7-8]。
- 位置偏差：LLM-as-a-Judge 把两个摘要顺序对调后结论显著不同，部分情形相反；RAG 对 Global 时 RAG 在 Comprehensiveness 上始终占优，Global 在 Diversity 上占优 [p.7]。
- 附录 M：为 RAG 增加取回块数以匹配 GraphRAG 的输入 token 后，RAG 略有提升，主要结论不变 [p.19]。

## 5. 作者陈述的局限
- 文中未设 Limitations 专节。结论处作者指出当前 GraphRAG 的实际问题：建图不完整或有噪声、计算与存储额外开销、摘要评测中 LLM-as-a-Judge 的位置效应 [p.8]。
- 作者在比较两个摘要实验时说明，与 Edge et al. 的结论不同源于任务（全局摘要 对 特定角色或事件的查询）与评测方式（无参考的 LLM-as-a-Judge 对 参考摘要的 ROUGE/BERTScore）[p.7]。

## 6. 原文摘录
- "RAG and GraphRAG exhibit complementary behaviors rather than a consistent winner." [p.2]
- "KG-based GraphRAG generally underperforms on QA due to limited graph coverage." [p.4]
- "It also performs poorly on Null queries in MultiHop-RAG (ideally answered as insufficient information)" [p.4]
- "Integration generally achieves higher performance than Selection. However, Selection processes each query using only a single method, making it more computationally efficient." [p.6]
- "simply concatenating RAG and GraphRAG evidence does not reliably improve alignment with detailed ground-truth summaries." [p.7]
- "reversing the order of presented summaries leads to substantially different, and in some cases opposite, judgments" [p.7]

## 7. 对本库的可用点（笔记者推断）
- 关系图：图检索的收益集中在需要串联多个事实的问题（MultiHop-RAG 的 Temporal 类，RAG 30.70 对 Community Local 50.60），在单跳细节问题上 RAG 更好。本库约 45% 的条款含显式交叉引用，这类边可用确定性规则抽取，不受论文中 KG 仅覆盖约 65% 答案实体这类 LLM 建图缺口影响；因此建议把引用边做成确定性邻接，在 cite_id 命中后再按边扩展，而不是对全库做 LLM 建图（层：relation graph）。
- 检索与排序：论文的 Selection 路由（先分类再选检索方式）可对应本库的"单点查找 vs 多跳链"：已知 cite_id 或 (scope, income, topic) 单元时走精确查找，需跨条款串联时才展开图。路由应由程序规则决定（有无编号、有无交叉引用），不能照搬论文用 LLM 做分类（层：retrieval & ranking、LLM boundary）。
- 成本：Table 4 显示建图时间和检索时间可高出一个数量级（135 s 对 7702 s）；本库引用边可在构建脚本里用正则抽取，成本近似线性，随库规模增长便于增量维护（层：scale & maintenance）。
- 评测：论文做"仅 A 对 / 仅 B 对"的混淆矩阵，可用于比较本库"精确匹配 / BM25 / 图扩展"各自独有命中的查询，以判断图扩展是否值得保留；评测集应分单跳与多跳（层：evaluation of retrieval）。
- 评测：LLM-as-a-Judge 的位置偏差表明，不应用 LLM 判官评价检索结果；改用 cite_id 级别的 gold 集合做确定性指标（层：evaluation of retrieval、LLM boundary）。
- 溯源：Community Global 和摘要类检索丢失细节，且在 Null 查询上幻觉风险高（19.27）；本库应只返回原文条款，不返回生成的摘要或社区报告，数值须逐字对照原文（层：provenance & verification）。
- 不适用：论文的 KG 抽取、社区摘要、RAPTOR 摘要全部依赖 LLM 生成，与"计算中无 LLM、每个数字可逐字追溯"冲突；它们最多可作为计算之外的草拟/浏览辅助，且不能进入库。论文数据集均为通用文本，没有法条的版本、生效期与现行有效约束。
