# Agent 输出诊断与整改建议

日期：2026-10-16。当前整合主线：`Asia-Tax-AI-Agent-main`，检查时 HEAD 为 `22cdb92`。

## 结论

当前输出混乱的首要原因是业务执行结果缺少统一的用户展示契约：FSIE 问答输出原文摘录，费用问答输出模型摘要，访谈输出固定模板，结构计算输出内部字段，多任务再把不同回复直接拼接。前端主要渲染这些已拼好的字符串，无法稳定控制主次、去重、引用位置和语言。

模型解析阶段已有 JSON 与字段校验，检索阶段已有权限、版本和哈希校验。因此，“要求模型输出 JSON”“再加一句简洁回答”不足以解决问题。建议保留现有规则、事实确认和编排机制，新增统一的答案组装边界，随后接入有证据约束的解释生成。

## 检查范围与限制

- 对工作区五个项目副本做目录、入口和版本关系检查；重点逐段检查当前整合主线的 `packages/chat`、`packages/agent`、`packages/domain_bridge`、前端对话/结构/来源组件、API 与相关测试和验收脚本。
- 对照 B 副本的关键输出文件，以及 tax engine 固定发布副本的运行说明，确认业务计算与对话展示的职责关系。未把各目录中的历史输出混为当前主线行为。
- 未逐页重读外部 PDF/PPTX/Word，也未核验税法内容；此次工作针对代码输出链路。
- 未读取模型凭据、调用模型、访问业务数据库或修改生产逻辑。
- 当前 Python 3.12.3 环境缺少 `pytest` 和 `langgraph`，未声称重跑完整测试。离线复现用 AST 提取现有纯函数后直接执行，不导入项目服务或加载 `.env`。

## 当前真实链路

```text
普通聊天 → 路由模型的 reply
FSIE 查资料 → legacy/hybrid → agent.knowledge.compose_answer → 摘录字符串
案件访谈 → agent.dialogue → 固定问题 / 事实清单字符串
一般费用 → chat.expenses → 单独的模型摘要 / 回退字符串
结构规划 → domain_bridge → 原始状态 + 结果组件 / 独立 Markdown
多任务 / 多工具 → hybrid.validate → 多份字符串用空行拼接
最后 → ChatService.commit_prepared → message.text → React Markdown
```

其中 `message.answer` 也被保存，但当前研究回复界面以 `message.text` 为正文，并继续展示 `research_results` 的来源片段。

## 离线复现

详细结果见同目录 `2026-10-16-output-audit-evidence.json`。

1. 给现有 `agent.knowledge.compose_answer` 七条合成证据：生成正文 3,827 字符，含七个原文块，每块都截为 500 字符，均未保留完整合成文本，且正文暴露内部证据 ID。现有摘录校验通过。
2. 按当前拼接方式合并两份完整回复：模拟资料提示出现两次。此项只复现字符串聚合行为，不声称完成了模型、图编排或浏览器端到端测试。
3. 给旧摘要校验器一条“有效原文引用 + 原文中不存在的无关解释”：校验仍通过。这说明逐字引用校验能够证明引用真实存在，不能单独证明解释由该引用支持。

第 3 点决定了后续不能仅把旧摘要函数接到主链路，就宣称解决了回答质量或税务正确性问题。

## 建议设计：统一结果，统一组装，按任务展示

### 1. 引入最终输出契约

建议新增 `packages/agent/response_contracts.py` 与 `response_assembler.py`。命名为建议，不是已实现模块。

```text
ResponseEnvelope
  schema_version, response_id, locale
  response_kind: chat / research / intake / analysis
  status: complete / partial / needs_input / unavailable
  lead: 当前问题的直接回应；不足时明确说明不能确认什么
  sections[]: 标题 + 类型化内容项 + evidence_refs / fact_refs / calculation_refs
  citations[]: 本次引用表；保留来源、定位、版本、哈希和原文摘录
  next_step?: 一个当前主动作，或一个绑定 question_id 的追问
  notices[]: 研究标识、范围、时效等类型化提示
  task_results[]: 每个用户请求的完成状态与阻塞原因
  audit_ref: 指向完整 trace / 版本 / 调用信息
```

这是服务端的最终响应契约。模型只可提出解释性内容，状态、引用可见性、事实版本、复核状态和动作必须由服务端填充或验证。正文、引用和审计记录保留同一版本关系。

各业务模块返回类型化结果；最终组装器负责选择内容、合并和输出。`ChatService.commit_prepared` 是校验、保存该结果的公共边界。`legacy`、`hybrid`、费用和结构路径都必须覆盖，不能只改其中一个。

### 2. 一轮只做一次最终组装

- 工具返回证据、缺口、计算和状态，不各自写完整的用户答案。
- 多任务先按原始任务身份组织；同一任务重试后，保留最后有效结果及必要失败说明。不同任务的有效结果都保留。
- 引用去重使用来源版本、单元身份和内容哈希；不能只按 URL 去重，避免把同一法规的不同条款或版本合并。
- 对同一证据的跨工具命中展示一个引用入口；历史尝试留在审计记录。
- 同类提示合并一次，同时保留确有差异的范围或时效限制。
- 最后统一确定一个当前追问；其他缺口列入待补清单，不能在每个小任务后重新启动访谈。

第一阶段可只用确定性模板完成组装，先消除重复和内部字段。第二阶段再用模型生成证据约束解释，避免一次改变所有环节。

### 3. 前端按内容类型展示

默认视图建议采用“直接回应 → 关键条件或发现 → 当前待补项 → 下一步”。来源以 `[1]`、`[2]` 等短引用连接可展开原文；技术 ID、哈希、任务 trace 放入详细信息。

不同任务使用相同数据契约、不同展示方式，不给简单问答强行套完整报告：

| 任务 | 默认展示 |
|---|---|
| 问候、产品用法 | 简短自然回复 |
| 单一条文、日期或概念查询 | 直接回应，附必要短引用；无关个案问题不追问 |
| 法律研究、多条件问题 | 核心回应 + 少量关键条件 + 引用入口 + 必要缺口 |
| 事实访谈 | 本轮新增信息 + 一个当前问题 |
| 多任务比较 | 按用户请求分小节，来源共用，提示合并 |
| 结构分析 | 可得结果 / 阻塞原因 + 有标签的资金流与数值 + 未决条件 |

已有 `AnswerText.tsx` 支持 Markdown/GFM，证据卡也已折叠，所以先改正文的来源和组织方式。字体、间距和动画排在后面。

### 4. 有证据约束的解释生成

当前可借鉴 `chat.answers` 的段落证据结构，但需要适配主链路的 `model_evidence`、权限和版本规则。

- 解释生成接收当前问题、明确选中的任务、合法证据投影，以及必要的已确认事实；不直接发送整个案件、display-only 原文或完整内部对象。
- 只在模型使用与展示权限均允许时生成可披露解释。受限材料保留许可范围内的原文展示和不足说明。
- 数值、币种、税额上下界和规则结果来自确定性计算；模型只能解释，不重新计算或改变结论状态。
- 检查 JSON、字段类型、逐字引用、引用版本、数字来源及与证据的支持关系。语义支持检查是额外质量环节，需要专业标注校准，不能承诺完全自动证明。
- 生成或校验失败时，回退到简短的“解释未通过核验 + 可查原文”，不把七段长原文重新塞回正文。
- 解释生成和修复共享既有执行预算。若每个工具调用都单独总结，会额外增加时延和成本；应在任务聚合后统一生成。

### 5. 统一语言与导出

建立字段值、状态、问题种类和常用动作的语言映射，覆盖模板分支及结构桥接分支。中文产品解释、英文原文引文可以并存，但必须明确区分。

UI 和 Markdown 导出共用同一规范化内容投影；审计附录保留完整版本和哈希。已冻结、绑定 `report_hash` 的历史报告不能原地改写；新稿采用新模板/输出版本并重新冻结。旧消息通过读时适配继续显示，未知字段退回旧视图。

## 实施顺序与完成条件

| 顺序 | 实施内容 | 完成条件 |
|---|---|---|
| 第一批：减少混乱 | 输出契约、确定性聚合、引用去重、状态/枚举映射、正文与原文展示分离 | 主链路、费用、结构、legacy/hybrid 均可输出一致结构；默认正文无原始对象和内部证据 ID；同类提示与同一来源不重复；独立任务不丢失 |
| 第二批：改善回答 | 聚合后的问题导向解释器，接入证据权限/支持校验和预算 | 回答直接回应问题，实质陈述可追溯；无证据不编造；失败可控回退；计算值与原结果完全一致 |
| 第三批：完成交付一致性 | 共享导出投影、历史适配、展示验收集及必要进度反馈 | 刷新/恢复不改变正文与引用关系；新报告版本可追溯；屏幕和导出含义一致；旧冻结稿哈希不变 |

暂不建议为输出问题重写 LangGraph、增加更多 agent、切换模型或重做知识库。现有编排和证据机制能复用，优先补上执行结果到用户答案之间的边界。

## 验收建议

保留现有权限、事实修订、幂等、预算、报告冻结和引用哈希测试，同时把依赖固定中文正文格式的断言迁移到结构化引用字段。

新增聚焦以下行为的验收：

1. 简单问题简短回应；复杂问题按任务分节；需要追问时只有一个当前主问题。
2. 七条来源、多工具命中同一来源、同任务重试、多任务部分失败：无无意义重复，保留全部独立任务结果与阻塞原因。
3. 中文/英文覆盖固定模板、枚举、结构结果和导出；原文引文不被擅自翻译或改写。
4. 未匹配、受限、超时、摘要校验失败都有可理解的降级展示。
5. 解释不能改变数值、币种、上下界、事实确认状态或复核状态；引用真实存在但不支持解释的样例必须单独评估。
6. 浏览器检查默认视图、展开原文、窄屏、复制和刷新恢复；不能只用后端通过数代替可读性验收。
7. 用一组未参与调整的合成问题和专业标注样例评估相关性、支持性及表达。机械检查与人工专业复核分别记录，避免把引用可追溯等同于税务正确。

本次只新增诊断文档和合成证据记录，业务修复尚未实施。
