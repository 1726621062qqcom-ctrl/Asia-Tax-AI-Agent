# Taxora 场景输出格式设计

日期：2026-10-16。状态：产品与文案设计稿，尚未修改提示词或业务代码。

## 1. 核心决定

正文随当前任务变化，法规依据统一放在回答最后。

用户先读到直接回应，再读必要解释和下一步；需要核实时，在末尾查看条款、官方来源与原文。现有原文展开、官方链接、定位、版本与哈希能力继续保留。

三个预设按钮是任务的快捷入口。默认对话框也能进入同样的输出模式；后续每轮根据当前问题选择格式，不能因为用户曾点击“境外股息”，就把日期查询、事实更正或问候都写成完整分析。

本稿示例用于说明表达和排版，`〔法规引用〕` 等为设计占位，不是已核验的税务回答。上线时只能使用该轮实际检索并支持正文的依据，不能把占位符发给用户。

## 2. 所有场景共用的表达原则

1. 第一至二句直接回应用户。能回答就给答案，不能判断就具体说清缺什么；不以“已找到可用资料”“依据覆盖不完整”等执行状态代替回答。
2. 一段处理一个意思。短问题可以只有一个自然段；清单、对比和复杂分析才使用小标题或表格。
3. 同一个事实只放在一个主要位置。已知事实、判断理由、待补事项各司其职，不在每个部分重复整段案情。
4. 把判断边界写在相关句子里。把“用户陈述”“规则核对结果”“尚待确认”区分清楚，避免每段后重复整套免责声明。
5. 使用用户能理解的词，如“还没确认”“两次说法不一致”“需要补充”。内部状态、字段名、证据 ID、JSON、哈希不进入默认正文。
6. 每轮最多一个主追问或主动作。其余待补项可列为清单，不能同时在多个模块里各问一遍。
7. 解释、下一步、必要的范围提示都放在引用之前。法规依据是整条回答的最后一个区域。
8. 引用跟随实际使用情况。纯问候和单纯确认事实不附无关法条；涉及规则、判断、材料要求或方案的陈述必须有相应支持依据。

## 3. 场景与内容结构

| 入口 / 当前任务 | 默认正文结构 | 通常篇幅 | 末尾依据 |
|---|---|---|---|
| 境外股息：一般咨询或个案分析 | 直接回应 → 关键理由或条件 → 必要待确认项 / 一个下一步 | 复杂分析约 300–600 字；简单问题更短 | 支持实际判断的条款；必要指引单列类型 |
| 梳理事实：尚未给案情、想知道准备什么 | 简短引导 → “需说明什么—可用什么材料核对”清单 → 一个开始问题 | 约 150–350 字 | 支持资料要求的条款或指引 |
| 梳理事实：已有案情 | 本轮整理说明 → 已知信息 → 影响后续判断的缺口 → 一个下一步 | 4–8 行事实 + 2–3 项优先缺口 | 有法规判断时列引用；仅复述事实时说明来源为用户陈述 |
| 查阅依据：条文、概念或官方案例 | 直接回答 → 与问题相关的解释 / 对比 → 必要适用限制 | 简单日期 1–3 句；一般规则约 150–350 字 | 精确到实际条款、指引段落或案例栏目 |
| 默认对话：补充、更正、小追问 | 回答本轮变化或问题 → 必要的一步提示 | 1–4 句 | 本轮用到法规时附；不机械重发上一轮全部文献 |
| 默认对话：方案 / 结构比较 | 当前能得出的结果 → 简明比较表 → 成立条件与未覆盖事项 → 下一步 | 约 400–700 字，按复杂度调整 | 支持每个方案差异的法规与指引；与计算结果对应 |
| 默认对话：多任务 | 一句总回应 → 按用户原问题分小节 → 统一下一步 | 按任务控制，避免每节都写完整报告 | 全文共用一份去重引用表 |
| 信息不足、检索失败或超出范围 | 具体说明限制 → 已能保留的有效结果 → 一个澄清问题或重试动作 | 约 50–150 字 | 有效引用照常保留；无证据时明确未取得，不展示空列表 |
| 问候、产品使用 | 自然直接回答 | 1–3 句 | 无需法规引用 |

上述篇幅是编辑目标，不能为了达标删掉决定性条件或补写无关内容。输出复杂度应随用户问题变化。

## 4. 三个预设入口的具体设计

### A. 境外股息

按钮初始问题是“分析境外股息的 FSIE 处理，需要先确认哪些事实？”。第一轮应回答这个准备问题，提供一份有主次的准备清单；不要把一般准备咨询直接变成要求用户完成全表的个案访谈。

用户提供具体交易后，再切入个案格式：

```text
〈先回应：现在能判断到哪一步；如果不能判断，具体说明原因。〉

关键在这几项：
1. 〈与这笔交易有关的一项条件；标明已知事实和待确认部分〉。[1]
2. 〈另一项真正影响结果的条件〉。[2]
3. 〈必要时才出现的第三项〉。

〈下一步只问一个当前最有价值的问题，或提出一个明确动作。〉

法规依据
[1] 〈法例名称 + 实际条/款〉——支持上文哪一点。〈官方链接；展开原文〉
[2] 〈法例或官方指引 + 实际定位〉——支持上文哪一点。〈官方链接；展开原文〉
```

语气示例：“目前还不能判断这笔股息是否适用豁免。你提供的持股信息已经记下，但有一项会影响后续分析的信息还没确认：〔具体缺失事实〕。先把这一项确认，我们再继续核对相关条件。”

如果用户只问“什么是 FSIE”，使用短解释格式，不展开其公司案情。

### B. 梳理事实

这里应优先交付一份用户容易核对的记录，不提前混入税务结论。

尚未提供案情时：

```text
可以，先按下面几类准备；暂时没有的信息可以先留空。

需要说明什么        可用什么材料核对
〈信息类别〉        〈对应材料；确有依据才称必需〉
〈信息类别〉        〈对应材料〉
〈信息类别〉        〈对应材料〉

我们先从〈一个信息类别〉开始：〈一个问题〉？

法规依据
〈只列本轮材料要求实际使用的条款或官方指引〉
```

已有案情时，用 GitHub 的合成案例说明排版：

```text
我把你目前提供的信息整理如下，持股比例已按你的更正改为 3%。

已知信息
收款方：在香港经营的公司，属于跨国集团
付款方：内地子公司
股息金额：100 万港币
持股比例及时间：3%，连续持有 18 个月
到账日期：2025 年 6 月 30 日

还需要核对
〈列出实际缺少、与当前目标相关的 2–3 项；同一缺口只列一次〉

〈一个最有价值的下一步问题〉？

〈若本轮只是复述：注明“以上根据你提供的信息整理，本轮未作新的法规判断。”〉
〈若解释了法规要求：最后附对应的法规依据。〉
```

“已知信息”只代表已记录用户陈述，不能自动变成“经证实的事实”。用户要求仅更正一个值时，只回复“已将持股比例从 20% 改为 3%，其他信息保持原记录”，不重发整张表。

### C. 查阅依据

先回答“这份依据说了什么、和我问的有什么关系”，末尾交付可核查出处。

```text
〈直接回答所问规则、条文位置、日期或案例信息。〉[1]

〈用普通语言解释与问题有关的 2–3 个要点。用户要求对比时再使用表格。〉

〈只有涉及个案套用时，补充尚需比较的事实、期间或限制。〉

法规依据 / 官方资料
[1] 〈具体法例条款 / 指引段落 / 官方案例栏目〉
    用途：〈这条依据支持什么〉
    〈官方链接〉  〈展开原文〉
```

几个重要变体：

- 用户问某个日期：一句日期答案，必要时一句说明，随后给日期所在栏目和原文。不要重讲整套制度。
- 用户要求法规原文：直接交付精确定位与可展开原文，按要求允许展开全文。避免在解释和来源卡里再复制同一段。
- 用户要求案例能否套用：先说是否已有足够信息比较，再按“案例事实—你的事实—尚缺比较信息”说明。引用标注为“官方预先裁定案例”，不能包装成普遍适用的法条。
- 用户问应读哪些资料：正文按问题说明查阅顺序，末尾来源区给完整标题和链接；两处通过编号关联，不重复堆两份文献清单。

## 5. 默认对话框的其他格式

### 方案与结构比较

先说明比较基于哪些已确认输入，以及现在是否已取得可比较结果。实际模型尚未算出结果时，不生成虚构的方案排名。

```text
〈目前得到的比较结果；结果不足时具体说明。〉

方案       主要差异       已计算结果 / 尚不能计算       成立条件
〈A〉      〈一项〉       〈来自规则引擎的值或范围〉   〈关键条件〉
〈B〉      〈一项〉       〈来自规则引擎的值或范围〉   〈关键条件〉

决定下一步的关键是〈一个条件或动作〉。〈必要时说明模型未覆盖的事项。〉

法规依据
〈与比较差异对应的引用；数值保持币种、期间和计算范围〉
```

“模型范围内税额上下界”必须保留其含义；不能改写成“保证税额”“全球最优”或未经支持的节税承诺。

### 多任务

按用户原问题分节，每节只回答那一部分。共同事实放在开头一次，未完成事项集中说明一次，所有引用在最后合并。

例如“先说明规则，再列材料”使用“规则怎么理解”“需要准备什么”两个小节，不能把两个完整 agent 答案连在一起。

### 缺信息与失败

用户没提供信息：“现在还不能确定〔具体问题〕，主要缺少〔具体事实〕。〔一个澄清问题〕？”

系统没取得证据：“这次没有取得能核对〔问题〕的官方原文，所以暂时不能可靠解释这一点。可以重试查询，或提供你希望核对的具体条款。”

二者不能混用。服务故障不应要求用户重新填写已提供事实。内部 `law|...`、检索拒绝原因、超时堆栈放在诊断详情，不进入答案。

## 6. 回答末尾的法规引用区

推荐使用统一的“法规依据”区域；包含非立法资料时标明类型，避免把指引或个别裁定称为法律条款。

每条默认显示：

```text
[1] 《〈法例名称〉》第〈条〉条第〈款〉款
    支持：〈正文中的具体判断或条件〉
    官方来源  ·  展开原文

[2] 〈主管机关〉〈指引名称〉第〈段〉段〔官方指引〕
    支持：〈对应说明〉
    官方来源  ·  展开原文
```

- 正文用 `[1]`、`[2]` 指向末尾引用，可点击定位。短回答也保留这种对应关系。
- 原文默认折叠，用户主动要求原文时展开。原文保留语言，解释跟随用户当前语言。
- 现有抓取时间、适用期间、来源版本和哈希保留在引用详情；重要的时效限制应在正文适用句或引用卡上明确提示。
- 同一来源、同一版本、同一条款及片段去重；同一网站下不同条款不能仅按 URL 合并。不同时间版本不能合并。
- 只展示本轮实际支持答案的来源，不把所有召回材料全部作为引用输出。需要继续查阅的资料另标为“延伸阅读”。
- 没有有效依据时明确说明未取得，不能制造引用，也不显示一个空的法规区。纯事实记录的来源是用户陈述。
- 完整回答复制时包含引用列表。引用与正文不能在刷新、历史恢复和导出时失去对应。
- “请补充信息”、范围提示和下一步都位于引用区之前。不能在引用之后又追加一段追问、重复免责声明或调度提示。

## 7. 去重与实现要求

产品层面需要一份最终答案、一个主追问、一份引用表。

执行模块可以分别产出检索、事实、计算和状态；最终组装阶段统一选择内容并去重。不要让每个工具分别生成整套“回答 + 条件 + 缺口 + 免责声明”。

建议保存独立字段：`answer_kind`、`lead`、`sections`、`next_step`、`notices`、`citations`。引用的底层 ID、版本、哈希不变，前端另生成可读编号。`next_step` 由受控工作流提供，生成模型不能擅自确认事实或修改复核状态。

现有 `Passages` 的原文与来源详情能力可复用。需要调整的是正文不再批量塞入长摘录、研究结果跨组去重，以及所有附加文案都在最终引用区之前完成组装。

## 8. 最小验收标准

1. 同一个测试问题通过预设或默认输入，语义和引用一致，表达允许随上下文变化。
2. 第一段能回答用户问题，或清楚指出具体不能回答的部分；不能只报告工具状态。
3. 日期追问与单字段更正保持简短；资料清单与比较使用列表或表格；不机械套同一个长模板。
4. 同一轮没有重复原文、重复事实段、重复限制提示或同一片段的重复引用卡。
5. 正文不含内部定位 ID、JSON、字段名或未翻译状态；保留必要术语并首次解释。
6. 实质税务陈述有相应依据，引用最后出现、定位真实、原文可查，且能支持其对应句子。逐字匹配不等于支持关系已被证明，仍需专门评估。
7. 连续追问只回答新问题；事实更正不继续使用旧值；多任务部分失败不丢掉已完成的有效结果。
8. 复制、刷新和下载后的正文—引用关系一致，旧冻结报告不被展示改造原地改写。

本轮先确定上述内容设计；线上测试记录另存于同目录，不将未完成的测试写成完整验收。
